## 1. Descripción general

**PDF Inspector & Signature Verifier** es un servicio web monolítico modular que analiza un documento PDF en un único ciclo de procesamiento y devuelve un informe JSON estructurado con:

- **Integridad criptográfica de las firmas digitales** (PAdES / CMS-PKCS#7): si la firma es matemáticamente válida y si el documento ha sido modificado después de firmarse.
- **Sellos de tiempo** (RFC 3161) y **cadena de confianza X.509** del firmante.
- **Revocación** (OCSP / CRL) como comprobación opcional y acotada.
- **Conformidad PDF/A-1b** mediante el módulo oficial *preflight* de Apache PDFBox.
- **Propiedades físicas**: versión, número de páginas, rotación y dimensiones por página, cifrado y permisos.
- **Veredicto general por firma** (✅/⚠️/❌) que resume integridad + cadena + revocación en una sola conclusión, con sus motivos explícitos (§2.13).

**Demo en línea:** <https://vps-651608c6.vps.ovh.net/> (HTTPS, sin login; sube PDFs de hasta 80 MB).

El servicio no guarda los documentos analizados: es **sin estado** y sin base de datos. Además de la API REST/Swagger UI, incluye una interfaz web estática ("Validar", §2.13) sin frameworks ni dependencias externas.

## 2. Cómo funciona

### 2.1 Flujo de análisis (objetivo)

```
Cliente (interfaz web "Validar" ✅ o Swagger UI ✅)
   │  POST /api/v1/pdf/analyze  (multipart, PDF ≤ 80 MB)          ✅
   ▼
api ──► application: AnalyzePdfUseCase                           ✅
            │ orquesta los puertos del dominio (ver §2.9)
            ├─► HashCalculator            SHA-256 / SHA-512       ✅
            ├─► PdfDocumentReader         estructura, páginas, permisos, XMP  ✅
            ├─► SignatureVerifier         /ByteRange + CMS + RFC 3161       ✅
            ├─► CertificateChainValidator PKIX contra trust store            ✅
            ├─► RevocationChecker         OCSP/CRL (opcional, timeout 2 s)   ✅
            ├─► PdfaConformanceValidator  preflight PDF/A-1b                 ✅
            └─► SignatureVerdictPolicy    veredicto por firma + global (§2.13) ✅
   ◄── PdfAnalysisReportDto (JSON) / ProblemDetail (error)
```

**En palabras sencillas.** Quien usa el servicio (desde la página web o desde Swagger UI) sube un PDF. El servicio lo pasa por una serie de comprobaciones, una detrás de otra, y responde con un único informe:

1. **Recepción.** Un *controlador* REST recibe el fichero (capa `api`). Si algo falla, responde con un error estándar (`ProblemDetail`) que explica la causa, en lugar de un mensaje técnico sin sentido.
2. **Orquestación.** Un único caso de uso, `AnalyzePdfUseCase`, decide el orden de las comprobaciones: calcula los hashes, lee la estructura del PDF, verifica cada firma, valida la cadena de confianza, consulta la revocación si se pidió y comprueba el formato PDF/A. Si una comprobación falla, las demás siguen adelante y el informe indica qué sección falló.
3. **Veredicto.** Con todos esos resultados, una política pura (`SignatureVerdictPolicy`) decide, firma por firma, si el documento es válido, no admitido o no válido, y por qué (§2.13).
4. **Respuesta.** Un *mapeador* convierte el resultado interno en un JSON pensado para el cliente (los DTOs), sin exponer las clases internas del dominio.

Spring conecta todas las piezas al arrancar la aplicación (§2.11). La página web «Validar» usa este mismo servicio (§2.13). La pantalla «Firmar» no lo usa: firma en el equipo del usuario con AutoFirma (§2.14).

**Cómo sabemos que funciona.** El caso de uso se prueba de tres maneras: tests unitarios de cada pieza, un test de integración con los componentes reales (PDFBox y Bouncy Castle), y un test completo que sube un PDF por HTTP y comprueba la respuesta. Además, las reglas de arquitectura de ArchUnit vigilan en cada compilación que cada capa solo dependa de la que debe (§2.9, §2.10).

### 2.2 Cómo se detecta que un documento ha cambiado después de firmarse

`infrastructure/bouncycastle/BcSignatureVerifier` implementa el puerto `SignatureVerifier` sobre PDFBox 3 (para leer los diccionarios de firma) y Bouncy Castle 1.86 (para el CMS), sin dejar escapar ningún tipo de esas librerías fuera del adaptador. Recorre **cada** campo de firma (`PDDocument#getSignatureFields()`) y evalúa cada uno de forma **independiente**, con su propio nombre de campo.

Una firma PDF no firma el fichero entero, sino los bytes indicados en el array **`/ByteRange`** del diccionario de firma. Ese array tiene cuatro números `[a b c d]`: dos tramos de bytes firmados que dejan un hueco en medio donde va la propia firma (`/Contents`, un contenedor CMS en hexadecimal).

La verificación comprueba, en este orden:

1. **Estructura del `/ByteRange`**: además de lo que ya valida el propio dominio (`ByteRangeCoverage`: empieza en 0, tramos sin solaparse, dentro del fichero), el adaptador comprueba a nivel de bytes que el hueco entre tramos está delimitado por `<`/`>` y que su longitud coincide exactamente con el tamaño hexadecimal de `/Contents`. Esta segunda comprobación se corrigió en la ronda de endurecimiento posterior a T04 (T04b): la longitud "esperada" se obtenía llamando a `PDSignature#getContents(byte[])`, que a su vez calcula los límites del propio hueco a partir de esos mismos números de `/ByteRange` -- comparar el hueco contra una longitud derivada del propio hueco es una tautología que nunca puede fallar. Ahora se usa `PDSignature#getContents()` (sin argumentos), que PDFBox resuelve de forma independiente recorriendo su propia estructura de objetos (tabla xref → diccionario → `/Contents`), sin usar en ningún momento los números de `/ByteRange`; un `/ByteRange` que declare un hueco de tamaño distinto al que realmente ocupa `/Contents` ahora se detecta. Un `/ByteRange` hostil o inconsistente (por ejemplo, una longitud negativa, que se sale del fichero, o que no coincide con `/Contents`) **nunca lanza una excepción**: se captura y esa firma se informa como `INVALID_SIGNATURE`, sin abortar el análisis de las demás firmas del documento.
2. **Integridad matemática (CMS)**: se lee `/Contents` con un único objeto ASN.1 (ver detalle técnico más abajo) y se verifica con Bouncy Castle (`SignerInformation#verify(...)`), que comprueba a la vez que el `messageDigest` firmado coincide con el resumen de los bytes cubiertos por `/ByteRange` y que la firma es válida para el certificado del firmante. Si un solo byte firmado cambia, la verificación falla (**`INVALID_SIGNATURE`**).
3. **Cobertura del fichero**: si el final del segundo tramo (`c + d`) alcanza el tamaño del fichero, la firma es **`INTACT`**. Si es menor, hay bytes añadidos **después** de firmar (una *actualización incremental*): la firma sigue siendo matemáticamente válida para su revisión, pero el resultado es **`MODIFIED_AFTER_SIGNING`**.

Con **varias firmas** (por ejemplo, un documento firmado dos veces) esto da un resultado que a primera vista sorprende pero es el comportamiento esperado de PDF: la **primera** firma queda como `MODIFIED_AFTER_SIGNING`, porque después de firmarse se le añadió una actualización incremental (la segunda firma); solo la **última** firma, cuyo `/ByteRange` alcanza el final real del fichero, es `INTACT`.

**Subfiltros soportados**: `adbe.pkcs7.detached` y `ETSI.CAdES.detached` se verifican por completo. `adbe.pkcs7.sha1`, `adbe.x509.rsa_sha1` y cualquier subfiltro desconocido se informan como **`UNSUPPORTED`** sin intentar verificarlos. `ETSI.RFC3161` (un sello de tiempo de *documento*, que no firma contenido sino que sella una revisión completa) se decidió mantener como `UNSUPPORTED`: verificarlo exigiría un camino de verificación distinto (interpretar el propio CMS como un `TimeStampToken` en lugar de como una firma CAdES normal, y un informe sin cadena de firmante en el sentido habitual), y el sello de **firma** (§2.6) cubre el caso que de verdad pide el TFM (demostrar cuándo se firmó una firma ya existente). Se documenta como decisión consciente, no como pendiente por omisión.

**Robustez frente a fallos parciales** (revisión posterior a T04, T04b): iterar los campos de firma de un documento hostil puede lanzar una excepción de tiempo de ejecución antes incluso de llegar al CMS (por ejemplo, al leer el nombre completo de un campo). Antes, esa excepción solo estaba protegida *dentro* de la evaluación del CMS/`ByteRange`, no en la lectura previa del campo; ahora todo el ciclo por campo (lectura + evaluación) está bajo la misma protección, así que un campo hostil nunca aborta el análisis de los demás. Además, si el CMS se verifica correctamente pero **no se puede volver a codificar** uno de los certificados extraídos a DER (un fallo de mapeo, no de criptografía), la firma ya no se informa como `INVALID_SIGNATURE`: se mantiene el `IntegrityStatus` real (calculado a partir del resultado criptográfico) con la cadena de certificados que sí se pudo mapear (parcial o vacía) y una nota de anomalía (`SignatureReport#anomaly`) explicando cuántos certificados no se pudieron mapear.

Estos casos (firma válida, byte manipulado, actualización incremental posterior, doble firma, `/ByteRange` hostil, subfiltro no soportado y campo de firma hostil) ya están demostrados con tests (ver [§7](#7-tests-y-calidad)).

#### Integridad de la firma frente a validez del certificado (T09c)

Analizando dos PDFs reales aparecieron dos casos que la implementación anterior no manejaba bien, ambos reproducidos ahora con *fixtures* generados por código (nunca con los PDFs reales, que contenían datos personales y no se han incorporado al repositorio):

1. **Un certificado firmante caducado en el momento de firmar** (caso real: certificado cualificado de Camerfirma con `notAfter` en mayo de 2026, firma con fecha de mayo... septiembre de 2026, es decir, firmado varios meses después de que el propio certificado hubiera caducado). Bouncy Castle, cuando el verificador (`SignerInformationVerifier`) se construye a partir de un `X509CertificateHolder` (el certificado completo, no solo su clave pública), comprueba **además** que ese certificado era válido en el instante que declara el atributo CMS firmado `signingTime`, y lanza `CMSVerifierCertificateNotValidException` si no lo era — con el efecto de que una firma criptográficamente íntegra se informaba como `INVALID_SIGNATURE`, con la cadena de certificados vacía y sin ninguna explicación.

   **Corrección**: la integridad criptográfica (¿coincide el `messageDigest` firmado con los bytes cubiertos por `/ByteRange`? ¿es válida la firma para la clave pública del firmante?) y la validez del certificado del firmante en el momento de firmar (¿podía firmar legítimamente en esa fecha?) son dos hechos independientes, no uno solo. Ahora el verificador se construye siempre a partir de la **clave pública** del firmante (nunca del certificado completo), de forma que Bouncy Castle nunca realiza esa comprobación de validez por su cuenta; la validez del certificado en el instante de firma se comprueba **por separado**, de forma explícita, y si no era válido se añade una nota de anomalía (`SignatureReport#anomaly`, p. ej. *"signer certificate was not valid at the declared signing time (notAfter ..., signed ...)"*) sin invalidar la integridad. La confianza/vigencia de la cadena (`chainStatus`) sigue siendo responsabilidad de `PkixCertificateChainValidator` (§2.7), que ya validaba en el instante de firma declarado y por tanto ya informaba `EXPIRED` correctamente para este caso — lo único que fallaba era que nunca llegaba a evaluarse, porque la firma se rechazaba antes.

2. **Un `digestAlgorithm` no estándar** (caso real: certificado cualificado de la FNMT, CMS **sin atributos firmados** — un PKCS#7 de estilo clásico, no CAdES —, con el campo `digestAlgorithm` del `SignerInfo` codificado como el OID del algoritmo de **firma** `sha256WithRSAEncryption` — `1.2.840.113549.1.1.11` — en lugar del OID del algoritmo de **resumen** `id-sha256` — `2.16.840.1.101.3.4.2.1` —, y encima con `digestEncryptionAlgorithm` codificado como un `rsaEncryption` a secas — `1.2.840.113549.1.1.1`, sin ningún resumen implícito). Es una codificación que no cumple RFC 5652 al pie de la letra, pero que Adobe acepta y que producen algunas herramientas de firma reales.

   Esto en realidad son **dos problemas encadenados**, el segundo mucho más sutil que el primero y encontrado solo al probar contra el fichero real (la reproducción sintética inicial, con atributos firmados, no lo detectaba):
   - Bouncy Castle, al intentar construir un calculador de resumen para el OID `sha256WithRSAEncryption` (mal usado como si fuera un OID de resumen), falla con `NoSuchAlgorithmException` (no hay ningún proveedor de resumen registrado bajo el OID de un algoritmo de firma).
   - Incluso arreglando eso, **`SignerInformation#verify(...)` seguía devolviendo `false`** para este fichero real concreto. Se investigó desensamblando el propio `SignerInformation.class` de `bcpkix-jdk18on` 1.86 (`javap -c`): para un CMS sin atributos firmados y una firma RSA, Bouncy Castle reconstruye el `DigestInfo` PKCS#1 que espera encontrar dentro de la firma directamente a partir del campo `digestAlgorithm` (aquí, mal etiquetado) — su propio método interno `translateBrokenRSAPkcs7` **solo corrige la variante histórica con SHA-1** de este mismo error (un `rsaEncryption` a secas junto a `sha1WithRSA`/`sha1WithRSAEncryption` como resumen), nunca las variantes SHA-224/256/384/512. El `DigestInfo` reconstruido acaba llevando el OID equivocado dentro, y la comparación byte a byte contra la firma real nunca coincide — un fallo *silencioso* (`verify()` devuelve `false`, no lanza excepción), y muy fácil de confundir con una firma genuinamente inválida.

   **Corrección**: cuando `digestAlgorithm` es en sí mismo un OID de algoritmo de firma **inequívoco** (tabla completa en `DigestAlgorithmOidNormalizer`: `sha1WithRSAEncryption`/`sha224WithRSAEncryption`/`sha256WithRSAEncryption`/`sha384WithRSAEncryption`/`sha512WithRSAEncryption`, `ecdsa-with-SHA1`/`224`/`256`/`384`/`512`, y `id-dsa-with-sha1` — deliberadamente **sin** `id-RSASSA-PSS`, cuyo resumen va en los propios parámetros del algoritmo, ni un `rsaEncryption` a secas, que no nombra ningún resumen), la verificación **no** pasa por `SignerInformation#verify(...)`: se construye un `ContentVerifier` directamente con ese mismo OID (que, tomado tal cual, ya es un algoritmo de firma completo y válido — el fichero real simplemente lo puso en el campo equivocado), evitando por completo la reconstrucción interna (defectuosa, para este caso) de Bouncy Castle. Cuando hay atributos firmados, se comprueba antes el `messageDigest` con el algoritmo de resumen ya normalizado (mismo mecanismo que el caso 1); cuando no los hay, se verifica directamente sobre los propios bytes firmados, tal cual haría un firmante real produciendo este formato. Cuando esta ruta se usó realmente, se añade una nota de anomalía (*"non-standard digestAlgorithm encoding (signature algorithm OID used instead of a digest OID)"*), sin invalidar la firma.

**La cadena de certificados nunca queda vacía solo porque la verificación fallara**: antes, cualquier fallo de `signerInformation.verify(...)` (incluido el caso 1 de arriba) descartaba también la cadena de certificados ya extraída del CMS. Ahora la cadena se extrae y se informa siempre que el propio CMS se pudo parsear (certificado del firmante localizado, certificados mapeados), aunque la verificación criptográfica falle de verdad (por ejemplo, un documento manipulado).

**`INVALID_SIGNATURE`/`UNSUPPORTED` siempre llevan un motivo legible (`anomaly`)**: antes de esta tarea, varias rutas de fallo dejaban `anomaly=null` (un `/ByteRange` hostil, un subfiltro no soportado, un campo de firma que lanza una excepción al leerlo). Ahora ninguna de esas rutas es muda — cada una explica, con un texto estable y no sensible, por qué el resultado no es `INTACT` (p. ej. *"messageDigest does not match the signed bytes"*, *"signature value does not verify"*, *"CMS container could not be parsed"*, o el propio mensaje estructural del `/ByteRange` como *"ByteRange gap is out of bounds: ..."*). El detalle real de una excepción inesperada nunca se traslada al cliente: se registra por log (`System.Logger`) y el motivo público siempre es un texto fijo y seguro.

### 2.6 Sellos de tiempo RFC 3161

Un sello de tiempo de **firma** (distinto del sello de tiempo de *documento* de §2.2) es un atributo CMS **no firmado** que una TSA (*Time-Stamping Authority*) añade a una firma ya existente: `id-aa-signatureTimeStampToken` (OID `1.2.840.113549.1.9.16.2.14`). Lo que sella no es el contenido del documento, sino **el valor de la propia firma** (los bytes de la firma RSA/DSA del firmante) — por eso puede añadirse *después* de firmar, sin invalidar la firma ni requerir volver a firmar nada.

**Por qué importa frente a la fecha de firma auto-declarada**: el diccionario de firma (`/M`) y el atributo CMS firmado `signingTime` son *auto-declarados* por el firmante — cualquiera con el certificado puede poner la fecha que quiera, sin ninguna garantía externa. Un sello de tiempo RFC 3161, en cambio, lo emite un tercero (la TSA) cuya propia firma puede verificarse: si el sello es válido, se tiene una prueba criptográficamente verificable de que la firma ya existía en ese instante, no solo la palabra del firmante. `TimestampInfo.genTime()` es esa fecha de la TSA; `claimedSigningTime` (en `SignatureReport`) sigue siendo la auto-declarada, y ambas conviven en el informe sin mezclarse.

**Verificación** (`infrastructure/bouncycastle/SignatureTimestampVerifier`), con Bouncy Castle `org.bouncycastle.tsp` (`TimeStampToken`), en dos partes independientes:

1. **Imprint del mensaje**: el sello declara un algoritmo de resumen y un valor (`messageImprint`). Se recalcula ese resumen —con el algoritmo que el propio sello declara, no uno fijo— sobre los bytes de la firma (`SignerInformation#getSignature()`) y se compara con el valor declarado. Si no coincide, el sello es inválido (`imprintValid=false`), pero **la integridad de la firma que lo contiene no se ve afectada**: son dos verificaciones independientes.
2. **Firma de la TSA**: el CMS del propio sello se verifica contra el certificado de la TSA embebido en él (`TimeStampToken#validate(...)`, construido con `JcaSimpleSignerInfoVerifierBuilder`), y se comprueba que ese certificado declara el uso extendido de clave `id-kp-timeStamping`; si no lo declara, no se rechaza la firma por eso, pero se añade una nota (`TimestampInfo#note`) — igual que con el atributo `signingCertificate`/`ESSCertID` del propio RFC 3161, que enlaza el sello a un certificado concreto y por tanto impide sustituirlo por otro sin invalidar la verificación.

**Casos límite, ninguno lanza una excepción**: sin sello → `TimestampInfo.absent()` (`genTime=null`). Sello con imprint incorrecto → `imprintValid=false`, pero la firma que lo contiene sigue `INTACT` si su propio CMS es válido. Sello con bytes ASN.1 corruptos o que no se puede parsear como `TimeStampToken` → se informa igualmente inválido (`genTime=null`, con una nota explicando el motivo), sin afectar a la integridad de la firma. **(T05b)** Si el sello se valida correctamente pero el certificado de la TSA no se puede volver a mapear a `CertificateInfo` (un fallo de codificación DER, no criptográfico — el mismo tipo de fallo ya tolerado para la cadena del firmante en §2.5), ya **no** se descarta todo el resultado del sello: `genTime`, `imprintValid` y `signatureValid` se conservan (son verificaciones independientes de si se pudo extraer el certificado) y solo se añade una nota indicando que los datos del certificado de la TSA no se pudieron mapear.

**Extensión mínima del dominio**: `TimestampInfo` ganó `signatureValid`, `tsaCertificate` (un `CertificateInfo`, reutilizando el tipo ya existente — el dominio sigue sin depender de ninguna librería de certificados) y `note`; `SignatureReport` ganó `anomaly` (ver más arriba) con el mismo propósito: informar una anomalía sin forzar al informe entero a un estado binario válido/inválido.

### 2.3 Modelo de dominio y puertos

El núcleo del sistema (`domain/`) es Java puro: no importa Spring, PDFBox ni Bouncy Castle (se comprueba en cada tarea). Todo el informe se modela con **records inmutables** que validan sus datos al construirse y copian las listas que reciben, para que nadie pueda modificarlas desde fuera.

| Concepto | Tipo | Regla que aplica |
|---|---|---|
| Informe completo | `PdfAnalysisReport` | Agrupa hashes, estructura, seguridad, PDF/A y firmas |
| Hashes | `DocumentHashes` | SHA-256 (64 hex) y SHA-512 (128 hex), en minúsculas |
| Página | `PageInfo`, `Box` | MediaBox/CropBox con ancho y alto calculados |
| Rotación | `Rotation` | Normaliza a 0/90/180/270 (`-90 → 270`, `450 → 90`); un valor que no sea múltiplo de 90 es inválido |
| Orientación | `Orientation` | Se calcula **después** de rotar: a 90° o 270° se intercambian ancho y alto |
| Cobertura de firma | `ByteRangeCoverage` | 4 valores, empieza en 0, tramos sin solaparse; indica si cubre todo el fichero |
| Estado de integridad | `IntegrityStatus` | `INTACT`, `MODIFIED_AFTER_SIGNING`, `INVALID_SIGNATURE`, `UNSUPPORTED` |
| Certificado | `CertificateInfo` | Sujeto, emisor, fechas, algoritmo, URLs OCSP/CRL y el certificado codificado (DER) |
| Sello de tiempo | `TimestampInfo` | `genTime`, `tsaName`, `imprintValid`, `signatureValid`, certificado de la TSA y una nota opcional; `absent()` cuando no hay sello |
| Cadena y revocación | `ChainStatus`, `RevocationStatus` | Empiezan como `NOT_CHECKED` y se completan más tarde; `ChainStatus` ya lo calcula `PkixCertificateChainValidator` (§2.7) |
| Error de sección **(T08b)** | `SectionError`, `AnalysisSection` | Cuando una sección guardada (`PDFA`, `SIGNATURES`) falla de forma inesperada, `PdfAnalysisReport.sectionErrors()` lo informa explícitamente, para que una lista de firmas vacía por ese motivo nunca sea indistinguible de "este documento no tiene firmas" |
| Veredicto por firma **(T11)** | `SignatureVerdict` (`SignatureReport.verdict()`/`verdictReasons()`) | `VALID`/`NOT_ADMITTED`/`INVALID`, calculado por la política pura `domain/policy/SignatureVerdictPolicy` (§2.13); empieza en `NOT_ADMITTED` (marcador seguro) hasta que la pasada final del caso de uso lo calcula de verdad |
| Veredicto del documento **(T11)** | `OverallVerdict` (`PdfAnalysisReport.overallVerdict()`) | El peor veredicto entre todas las firmas, o `NO_SIGNATURES` si no hay ninguna; método calculado, no un componente almacenado del record (§2.13) |

Los **puertos** son interfaces pequeñas que la infraestructura implementará con las librerías: `HashCalculator`, `PdfDocumentReader`, `SignatureVerifier`, `CertificateChainValidator`, `RevocationChecker` y `PdfaConformanceValidator`.

El verificador de firmas devuelve cada `SignatureReport` con la cadena y la revocación sin comprobar. Después, el caso de uso las completa con `withChainAndRevocation(...)`. Así cada adaptador tiene una sola responsabilidad y la revocación puede omitirse sin tocar el verificador.

> **Detalle técnico**: PDFBox reserva un hueco fijo para `/Contents` y lo rellena con ceros. Al extraer la firma hay que leer un único objeto ASN.1 (`ASN1InputStream.readObject()`), porque el constructor directo de `CMSSignedData` de Bouncy Castle rechaza los bytes de relleno ("Extra data detected in stream").

### 2.4 Lectura de estructura, seguridad y declaración PDF/A

`infrastructure/pdfbox/PdfBoxDocumentReader` implementa el puerto `PdfDocumentReader` sobre PDFBox 3 y `xmpbox`, sin dejar escapar ningún tipo de esas librerías fuera del adaptador:

- **Versión**: la de cabecera se extrae directamente de los primeros bytes (`%PDF-x.y`, expresión regular); la del catálogo, con `PDDocumentCatalog#getVersion()` (puede ser `null` si el documento no la declara). Si no se encuentra la cabecera `%PDF-` en los primeros 1024 bytes pero PDFBox consigue igualmente parsear el fichero (algo que los lectores de PDF, incluido PDFBox, tratan con tolerancia), `headerVersion` se informa como `null` ("desconocida") en vez de abortar el análisis.
- **Rotación por página**: se lee el atributo raw `/Rotate` con `PDPageTree#getInheritableAttribute`, que además de heredar el valor desde un nodo `/Pages` superior (cuando la página no lo declara ella misma) devuelve el valor **sin normalizar**. Se prefiere a `PDPage#getRotation()` porque este último ya normaliza y hereda, pero cuando el valor no es múltiplo de 90 lo convierte silenciosamente en `0`, ocultando la anomalía. Solo un `COSInteger`, o un `COSFloat` sin parte decimal (p. ej. `90.0`), se considera válido; un real no entero (p. ej. `90.5`) o un valor no numérico se marca inválido **sin truncarlo silenciosamente** -truncar `90.5` a `90` haría parecer válido un valor que no lo es-. El raw pasa por `Rotation.tryFromDegrees(...)`: si es válido se usa para calcular la orientación; si no, `PageInfo` lo expone igualmente (`rawRotation`, `rotationValid()`, ambos consistentes con `rotation` por construcción) y la orientación se calcula como si fuera `0°`, sin abortar el análisis.
- **MediaBox / CropBox y orientación**: se leen con `PDPage#getMediaBox()`/`getCropBox()` (esta última ya hereda de la MediaBox si no está declarada) y se calcula la orientación después de aplicar la rotación efectiva.
- **Número de revisiones**: `infrastructure/pdfbox/RevisionCounter` recorre la cadena de referencias cruzadas (`xref`/`trailer`) siguiendo los enlaces `/Prev` desde el último `startxref` hacia atrás, contando una revisión por cada sección de xref visitada, en vez de contar apariciones del marcador `%%EOF`. Ese conteo por marcador sobrestima los PDF *linealizados* (los que llevan una sección de xref adicional al principio del fichero para "vista web rápida" de Adobe): esa sección adicional está encadenada por `/Prev` igual que una actualización incremental real, pero es la **misma** revisión lógica, no una nueva. `RevisionCounter` detecta esta situación buscando la marca `/Linearized` cerca del principio del fichero y, si la encuentra, no cuenta esa sección de xref como una revisión aparte. PDFBox no genera ficheros linealizados al guardar, así que este caso se prueba con una estructura de bytes construida a mano en el test (dos secciones de xref con `/Prev`, la primera precedida por un diccionario mínimo de linealización), no con un fixture real. Sigue siendo una heurística a nivel de bytes -un fichero deliberadamente hostil podría falsear los enlaces `/Prev`- con una salvaguarda contra bucles infinitos (un conjunto de posiciones ya visitadas detiene el recorrido en cuanto una vuelve a aparecer, en vez de repetirla) y una vuelta al conteo por `%%EOF` si no se encuentra ninguna cadena de xref o si el `startxref` declarado cae fuera del fichero.
  - **Rendimiento** (revisión posterior a T04, T04b): la implementación original volvía a recorrer el fichero completo, desde el principio de cada sección hasta el final, en **cada** salto de la cadena `/Prev` -- coste cuadrático en ficheros con muchas revisiones (varios segundos en un fichero sintético de ~5 MB con 2000 revisiones). Ahora localiza de una sola pasada, por cada palabra clave relevante (`stream`, `startxref`, `/Prev`), todas sus apariciones ordenadas, y cada salto de la cadena las busca con una búsqueda binaria en vez de volver a recorrer el fichero: coste total `O(n log n)` en vez de `O(saltos × n)`, verificado con el mismo fichero sintético de 2000 revisiones (por debajo de 3 segundos, frente a los ~9,6 s de la versión anterior).
- **Cifrado y permisos**: `PDDocument#isEncrypted()` más `AccessPermission`, mapeado a los ocho valores de `Permission`. Un documento sin contraseña de usuario (o con contraseña de usuario vacía) se abre y se informan sus restricciones reales; uno con contraseña de usuario no vacía no puede abrirse y lanza `EncryptedPdfException`.
- **Declaración PDF/A (XMP)**: se exportan los metadatos XMP del catálogo (`PDMetadata`) y se parsean con `DomXmpParser` (del artefacto `xmpbox`, dependencia transitiva de `preflight`, ya en el classpath), extrayendo `pdfaid:part`/`pdfaid:conformance` del esquema `PDFAIdentificationSchema`. Sin metadatos XMP, o sin ese esquema, o con XMP corrupto, se informa `PdfaDeclaration.NONE` en lugar de fallar todo el análisis. Esto es solo la *declaración*; la validación formal PDF/A-1b con *preflight* llega en una tarea posterior.
- Cualquier fichero que PDFBox no pueda parsear (corrupto o que no sea un PDF) lanza `InvalidPdfException`, envolviendo la `IOException` original.

`infrastructure/crypto/JcaHashCalculator` implementa `HashCalculator` con `java.security.MessageDigest` (SHA-256/SHA-512) y `HexFormat`, sin depender de PDFBox ni Bouncy Castle.

### 2.5 Extracción de certificados

Para cada firma con una verificación CMS válida, `BcSignatureVerifier` extrae del propio CMS el certificado del firmante y todos los certificados incluidos (normalmente firmante + emisor), y los mapea a `CertificateInfo` (sujeto y emisor en formato X.500, número de serie en hexadecimal, fechas de validez, algoritmo de firma, certificado codificado en DER). La cadena se ordena **firmante primero**, siguiendo el emisor de cada certificado hasta llegar a uno autofirmado (la raíz) o hasta que no se encuentre el siguiente emisor dentro del propio CMS.

De cada certificado se leen además las URLs de sus extensiones **Authority Information Access** (OCSP) y **CRL Distribution Points**, si las declara. Una extensión ausente o mal formada no invalida el certificado: simplemente se informa sin URLs para esa extensión (**T05b**: probado también directamente para el propio mapeador, no solo de forma indirecta a través de un PDF real). La comprobación de revocación (`revocation`) queda, por ahora, como `notChecked()` — la completará el caso de uso en una tarea posterior (T10). La validación de la cadena contra un almacén de confianza (`chainStatus`) ya está implementada (§2.7); su integración en el caso de uso llega en T08.

### 2.7 Cadena de confianza X.509 (PKIX)

`infrastructure/pki/PkixCertificateChainValidator` implementa el puerto `CertificateChainValidator` con la implementación PKIX de la propia JDK (`java.security.cert.CertPathBuilder` + `PKIXBuilderParameters`), sin depender de Bouncy Castle para esta parte — el dominio (`CertificateChainValidator`, `ChainStatus`) sigue sin conocer ningún tipo de certificados.

- **Momento de validación**: `validate(chain, validationTime)` recibe el `Instant` contra el que se comprueban vigencia y confianza; **quién decide ese instante es el caso de uso** (T08), no este adaptador — será el sello de tiempo RFC 3161 si es válido, si no la fecha de firma auto-declarada, y si no hay ninguna, el instante actual.
- **Revocación deliberadamente desactivada aquí** (`setRevocationEnabled(false)`): comprobar OCSP/CRL es responsabilidad de T10, aplicada por separado una vez la cadena ya es de confianza.
- **Estados** (`ChainStatus`): `TRUSTED` (la ruta se construye y todos los certificados son de confianza), `UNTRUSTED_ROOT` (la cadena llega a un certificado autofirmado, pero no está en el almacén configurado), `INCOMPLETE_CHAIN` (falta un emisor: la cadena no llega a ningún certificado autofirmado), `EXPIRED` (algún certificado de la cadena presentada está fuera de su periodo de validez en `validationTime` — esta comprobación es previa e independiente de PKIX), `NOT_CHECKED` (lista vacía).
- **Cómo se distingue `UNTRUSTED_ROOT` de `INCOMPLETE_CHAIN`**: el `CertPathBuilder` de la JDK no siempre distingue estos dos motivos de fallo de forma estable entre versiones, así que ante un fallo de construcción de ruta se aplica una comprobación propia, independiente: ¿la cadena presentada es *estructuralmente completa* (cada certificado verifica criptográficamente contra la clave pública del siguiente, hasta llegar a uno autofirmado)? Si lo es, el problema es que esa raíz no es de confianza (`UNTRUSTED_ROOT`); si no llega a ninguna raíz autofirmada, falta un eslabón (`INCOMPLETE_CHAIN`).
- **Almacén de confianza** (`TrustAnchorProvider`): combina, de forma aditiva, (a) las raíces españolas empaquetadas en `src/main/resources/truststore/` (classpath), y (b) opcionalmente un directorio externo de certificados y/o un fichero PKCS#12, ambos como parámetros del constructor por ahora (la configuración por propiedades de Spring llega en T09).
- **Sin lista de confianza europea (TSL/EU LOTL)**: la cadena se valida contra el almacén propio de raíces españolas descrito abajo, no contra la lista de confianza de la UE — decisión ya reflejada en [§10](#10-decisiones-técnicas).

**Anclas de confianza empaquetadas** (`src/main/resources/truststore/`, con procedencia completa y huellas SHA-256 en `truststore/SOURCES.md`) — la mayoría son raíces autofirmadas, pero no todas (ver más abajo):

Ninguna ancla se incluye sin esa verificación independiente. Los dos ficheros FNMT usan la extensión `.crt` en vez de `.pem` (mismo contenido PEM) por una razón puramente local, no técnica: un guardián de seguridad de este puesto de trabajo bloquea el acceso a cualquier ruta `*.pem`/`*.key` para evitar leer/escribir material de clave privada, y coincidía también con estos certificados públicos por extensión — ver `truststore/SOURCES.md` para el detalle.

**No todas las anclas son raíces autofirmadas**: el modelo eIDAS de Listas de Confianza de la UE publica la CA **emisora** cualificada como servicio de confianza, no necesariamente su propia raíz (que puede ni siquiera estar publicada). "AC CAMERFIRMA FOR LEGAL PERSONS - 2016" es exactamente ese caso: su propio emisor, "CHAMBERS OF COMMERCE ROOT - 2016", no está publicado en la Lista de Confianza española. `PkixCertificateChainValidator` funciona igual con un ancla no autofirmada — el `CertPathBuilder` de la JDK resuelve una ruta en cuanto alcanza *cualquier* certificado configurado como ancla, autofirmado o no —, comprobado explícitamente con un test dedicado (`PkixCertificateChainValidatorTest#aChainAnchoredAtANonSelfSignedIntermediateIsTrusted`, con una cadena de tres niveles donde el ancla es la CA intermedia, no la raíz). Nota aparte: Mozilla, Google y Apple retiraron las raíces de Camerfirma de sus almacenes de confianza **TLS** entre 2021 y 2022 (una serie de incidentes/hallazgos de cumplimiento); esa retirada es específicamente sobre confianza TLS/web y no afecta a la posición de esta CA emisora cualificada en la confianza eIDAS para firma de documentos, que sigue las Listas de Confianza propias de la UE, con independencia de los programas de confianza de los navegadores.

**Por qué las CA emisoras de FNMT son anclas aunque su raíz ya está empaquetada (T09d)**: a diferencia del caso Camerfirma, `AC RAIZ FNMT-RCM` **sí** está ya en el almacén. Aun así, un PDF real firmado con un certificado FNMT solo trae en su CMS el certificado del firmante — nunca esta CA intermedia —, así que la ruta PKIX se queda a un paso de la raíz ya confiable y el análisis informaba `INCOMPLETE_CHAIN` (comprobado con un PDF real de usuario). Configurar la propia CA intermedia como ancla adicional permite que el `CertPathBuilder` termine la ruta ahí directamente, sin que el CMS tenga que incluirla ni que este servicio tenga que ir a buscarla (p. ej. por AIA). Solo se evaluaron los tres servicios CA/QC que pedía la tarea ("AC FNMT Usuarios", "AC Representación" y "AC Componentes Informáticos"); los dos últimos resultaron ser el mismo certificado subyacente (comprobado byte a byte contra la propia TSL), de ahí que solo se empaquetaran dos ficheros. El resto de servicios FNMT de la misma TSL (las CA "G2", "AC Sector Público", "AC Consulares", los servicios TSA, y varios servicios CA/QC retirados) quedan fuera de esta tarea. Verificado con `PkixCertificateChainValidatorTest#aChainOmittingAnIntermediateNotEmbeddedInTheCmsIsTrustedWhenThatIntermediateIsTheAnchor` (una cadena presentada con solo el certificado del firmante, sin la intermedia) y con la ejecución manual real descrita en §7/§11.

**Cómo añadir raíces propias**: sin tocar el código, pasando un directorio externo (un certificado por fichero, PEM o DER) y/o un fichero PKCS#12 al construir `TrustAnchorProvider` — se combinan con las raíces empaquetadas, nunca las sustituyen.

**Endurecimiento (T06b, revisión posterior a T06)**:

- `RevisionCounter` guardaba su contador de pasos de escaneo (diagnóstico solo para tests) en un campo `static` — inofensivo con un test en un solo hilo, pero una condición de carrera real en cuanto el servicio atienda peticiones concurrentes (un `reset` de una llamada podía pisar el conteo de otra en curso). Se sustituyó por una instancia local (`ScanStats`) creada en cada llamada y pasada como parámetro por todo el recorrido: no queda ningún estado compartido mutable. Probado con 16 hilos ejecutando `count(...)` concurrentemente sobre distintos documentos, comprobando que cada uno obtiene exactamente el conteo que le corresponde.
- `PkixCertificateChainValidator`: un certificado que no se podía volver a parsear desde su codificación DER (bytes hostiles o corruptos) lanzaba una `IllegalStateException` sin capturar. Ahora se informa como `INCOMPLETE_CHAIN` (un certificado que ni siquiera se puede parsear no aporta ningún enlace verificable a la cadena) en vez de abortar el análisis; el fallo concreto se registra por log para diagnóstico.
- `TrustAnchorProvider`: el directorio externo y el fichero PKCS#12 ya tienen tests propios (directorio temporal con certificados PEM/DER válidos y un fichero inválido; PKCS#12 real generado en el propio test). Un fichero no válido dentro del directorio externo ya no aborta la carga completa del almacén: se omite (y se registra por log), igual que el resto de adaptadores del proyecto ante una entrada hostil aislada.
- `TrustAnchorProviderTest`: la comprobación "las raíces no han caducado" comparaba contra `Instant.now()` — una bomba de tiempo, porque la raíz que antes caduca (FNMT-RCM, 2030-01-01) empezaría a fallar el test años antes de que el certificado necesite reemplazarse de verdad. Ahora compara contra una fecha de referencia fija (2026-09-27).

### 2.8 Validación formal PDF/A-1b (*preflight*)

`infrastructure/preflight/PreflightPdfaValidator` implementa el puerto `PdfaConformanceValidator` con el módulo *preflight* de Apache PDFBox (`PreflightParser` + `PreflightDocument`), validando **siempre** contra el nivel PDF/A-1b, sin mirar la declaración XMP del propio documento para decidir si validar o no.

**Por qué solo PDF/A-1b**: *preflight* 3.0.8 no valida formalmente PDF/A-2 ni PDF/A-3 (solo 1a/1b). El puerto documenta este contrato explícitamente: un documento que declare PDF/A-2/3 en su XMP se valida igualmente contra las reglas 1b (que casi seguro no cumplirá, porque 2/3 permiten construcciones que 1b prohíbe) y el resultado se informa como `NON_COMPLIANT` con incidencias específicas de 1b — decidir que eso significa en realidad "solo se valida formalmente PDF/A-1b" en vez de "no es conforme" es responsabilidad del caso de uso (T08), que combina este resultado con `PdfDocumentReader#readPdfaDeclaration`, no de este adaptador.

**Qué comprueba PDF/A-1b** (a grandes rasgos, verificado empíricamente contra los fixtures de este proyecto): fuentes embebidas (un documento con texto en una fuente estándar no embebida, como Helvetica, incumple), un `OutputIntent` con perfil de color declarado para cualquier operador de color, sin flujos de referencias cruzadas comprimidos (`/XRef` de tipo *stream*, introducidos en PDF 1.5 — PDF/A-1 se basa en PDF 1.4), metadatos XMP presentes y coherentes, sin cifrado, entre otras reglas del propio *preflight*.

**Nunca lanza excepción por un documento individual, con una única excepción deliberada**: solo una entrada que ni siquiera declara una cabecera `%PDF-x.y` reconocible lanza la `InvalidPdfException` del dominio — más estrecho que `PdfBoxDocumentReader`, que lanza esa misma excepción para cualquier entrada que PDFBox no pueda parsear, incluida una truncada que sí declara cabecera. Un documento cifrado, uno con cabecera pero por lo demás roto, o un fallo interno del propio *preflight* se informan como `NOT_VALIDATED` con una incidencia explicativa, nunca se lanzan — un veredicto de conformidad ("no se puede validar") sigue siendo útil para el resto del análisis aunque el documento esté más roto de lo que PDFBox puro puede abrir.

**Diseño: una comprobación previa antes del *parseo* real de *preflight***: antes de invocar *preflight*, el documento se carga una vez con PDFBox normal (`Loader#loadPDF`) solo para distinguir cifrado de "cabecera presente pero roto". Esto supone un segundo *parseo* completo además del que hace el propio *preflight* — una preocupación de rendimiento real, aunque modesta, para un módulo ya de por sí pesado; sin medir todavía (perfilado de memoria/rendimiento es tarea de T12), pero queda anotado aquí.

**Incidencias**: cada resultado no conforme trae una lista de `PdfaIssue` (código + mensaje) deduplicada (mismo código y mensaje se cuentan una sola vez) y acotada a 200 elementos (con una incidencia `TRUNCATED` indicando cuántas se omitieron), para que un documento con un problema sistémico no produzca miles de incidencias casi idénticas.

**Incidencias bilingües (T11g)**: cada incidencia de la API lleva `code`, `message` (el texto original en inglés de PDFBox) y `messageEs` (descripción en español, o `null`). La traducción la resuelve `domain/model/PdfaIssueCatalog`, un catálogo de datos puro (solo `java.util`, sin dependencias de PDFBox, así que `ArchitectureTest` sigue en verde) con una entrada por cada código `ERROR_*` de `org.apache.pdfbox.preflight.PreflightConstants` de *preflight* 3.0.8 (verificados con `javap -constants`, no supuestos): las ocho categorías (`1` sintaxis, `2` gráficos/color, `3` fuentes, `4` transparencia, `5` anotaciones, `6` acciones, `7` metadatos XMP, `8` procesamiento), sus subcategorías y todas las hojas. La búsqueda prueba primero el código exacto y, si no existe, sube por su categoría un segmento cada vez (`3.1.99` → `3.1` → `3`). Un código sin traducción (por ejemplo `-1`, `ERROR_UNKNOWN_ERROR`, o los códigos sintéticos del proyecto `NOT_VALIDATED` y `TRUNCATED`) devuelve `messageEs = null` y la interfaz muestra solo el mensaje en inglés; nunca se inventa una traducción. En la interfaz, cada incidencia muestra primero el español y debajo, más pequeño y en cursiva, el original en inglés (`lang="en"`), siempre con `textContent`.

**Fixture conforme** (`TestPdfFactory#pdfA1bCompliant`): el documento más pequeño que este proyecto pudo construir y que *preflight* valida como conforme es una página en blanco (sin texto, así que no hace falta embeber ninguna fuente — evita por completo la cuestión de licencias de fuentes) con un `OutputIntent` sRGB y XMP `pdfaid` (parte 1, conformidad B). Se probó también con `TestPdfFactory#unsigned()` (sin `OutputIntent` ni XMP) para el caso `NON_COMPLIANT`, con códigos de error reales de *preflight* capturados empíricamente (`3.1.3` fuente no embebida, `2.4.3` operador de color sin perfil, `7.1` sin metadatos PDF/A).

**(T07b)** El `OutputIntent` sRGB de ese fixture usaba originalmente el perfil ICC del propio Windows (`C:\Windows\System32\spool\drivers\color\sRGB Color Space Profile.icm`, leído solo en tiempo de test), lo que dejaba el test de la ruta `COMPLIANT` saltado (no fallado, pero tampoco probado) en el runner de CI, que es Linux. Ahora usa el perfil sRGB que trae el propio JDK (`java.awt.color.ICC_Profile.getInstance(ColorSpace.CS_sRGB).getData()`): comprobado empíricamente que *preflight* lo acepta igual como fuente válida de `OutputIntent`, sin necesidad de entorno gráfico (la implementación es Little CMS, no un servicio de color del sistema operativo), así que el test ya no se salta en ninguna plataforma.

**(T07b) Endurecimiento adicional**: la comprobación previa de cifrado/documento roto (antes de invocar *preflight*) ahora también captura una `RuntimeException` inesperada, no solo `IOException`/`InvalidPasswordException`, informando `NOT_VALIDATED` en vez de dejarla escapar. `PreflightPdfaValidatorTest` añadió cobertura directa de la rama `probe.isEncrypted()` (documento cifrado con contraseña de usuario vacía, distinta de la rama de excepción ya cubierta) y de la truncación/deduplicación de incidencias a 200 (probada llamando directamente al mapeador de errores, package-private, con una lista sintética de 250 incidencias — construir un documento real con más de 200 errores distintos de *preflight* no era práctico).

### 2.9 Orquestación: `AnalyzePdfUseCase` (T08)

`application/AnalyzePdfUseCase` es una clase de Java puro (sin Spring todavía; el cableado llega en T09) que orquesta, en un único método `analyze(fileName, content, options)`, todos los puertos del dominio descritos arriba, en este orden: hashes → estructura/seguridad/declaración PDF/A → validación formal PDF/A-1b (combinada con la declaración, ver más abajo) → firmas (cada una enriquecida con cadena de confianza y, opcionalmente, revocación). Recibe también un `java.time.Clock` inyectado (nunca `Instant.now()` directamente), para que `analyzedAt` y el "ahora" usado como último recurso de `validationTime` sean deterministas en los tests.

**Cómo se decide `validationTime` para la cadena de confianza** (§2.7): para cada firma, por este orden de preferencia — (1) el `genTime` del sello de tiempo RFC 3161 de la firma, solo si ese sello es válido (`imprintValid` y `signatureValid` ambos `true`); (2) si no, la fecha de firma auto-declarada (`claimedSigningTime`); (3) si tampoco hay, el instante actual del `Clock` inyectado. Esto es exactamente lo que ya documentaba `PkixCertificateChainValidator`, ahora implementado por quien realmente puede decidirlo (el caso de uso, no el adaptador).

**Combinación de la validación PDF/A** (contrato de §2.8): el caso de uso lee la declaración XMP `pdfaid` con `PdfDocumentReader#readPdfaDeclaration` y, por separado, el resultado formal 1b con `PdfaConformanceValidator#validate`. Si el documento declara PDF/A-2 o PDF/A-3 (`part != 1`), el informe final es `NOT_VALIDATED` con una incidencia `PDFA_PART_NOT_SUPPORTED` explicando que solo se valida formalmente PDF/A-1b — en vez del resultado formal 1b (casi con toda seguridad `NON_COMPLIANT`, con incidencias que no dicen nada real sobre la conformidad 2/3 del documento). Si declara PDF/A-1 o no declara ningún PDF/A, se usa el resultado formal tal cual.

**Revocación** (§2.12, §10, opcional; implementación real desde T10): si `AnalysisOptions.checkRevocation()` es `false`, cada firma recibe `RevocationStatus.notChecked()` sin llamar a ningún `RevocationChecker`. Si es `true`, **solo se llama al `RevocationChecker` cuando la cadena de esa firma ya es `TRUSTED`**; para cualquier otro estado (`UNTRUSTED_ROOT`, `INCOMPLETE_CHAIN`, `EXPIRED`, `NOT_CHECKED`) se informa `NOT_CHECKED` con el detalle `"revocation not checked: certificate chain is not trusted"`, sin invocar al *checker* en absoluto — decisión de seguridad explicada en §2.12. Cuando la cadena sí es de confianza, el certificado del firmante y su emisor inmediato para la consulta de revocación **no** se toman directamente de `signature.chain()` (la cadena tal cual la extrajo `SignatureVerifier` del CMS, que un atacante controla), sino de `CertificateChainValidator#validatedPath` — los certificados que PKIX realmente usó para llegar a ese veredicto de confianza; ver §2.12 para el porqué. `application/NoOpRevocationChecker` (usado ahora solo en un test de integración) queda como referencia histórica de la implementación provisional anterior a T10.

**Documento cifrado o corrupto: se propaga, no se atrapa**: `readStructure`/`readSecurity`/`readPdfaDeclaration` pueden lanzar `EncryptedPdfException` (contraseña de usuario no vacía) o `InvalidPdfException` (entrada corrupta o que no es un PDF). Ambas se propagan sin capturar fuera de `analyze(...)`: no existe un informe parcial razonable para un documento que ni siquiera se pudo abrir, y la futura capa REST (T09) debe mapear ambas a un `422`. Decisión documentada explícitamente en el Javadoc de la clase, no un descuido.

**Resiliencia: el fallo de una sección no debe perder el resto del informe**: dos adaptadores cuyo propio contrato ya dice que no deberían lanzar excepciones para un documento individual reciben, además, una guarda propia en el caso de uso (defensa en profundidad frente a un fallo inesperado del adaptador, no frente a su comportamiento documentado):

- `PdfaConformanceValidator#validate`: una `RuntimeException` inesperada se informa como `NOT_VALIDATED` con una incidencia explicativa, sin perder hashes/estructura/seguridad/firmas ya calculados.
- `SignatureVerifier#verify`: una `RuntimeException` inesperada se informa como "sin firmas" (lista vacía) — no hay una firma individual a la que aislar el fallo, porque ocurrió antes de poder extraer ninguna.
- Enriquecimiento por firma (validación de cadena + revocación): guardados juntos; un fallo dentro de uno u otro deja esa firma con sus campos de integridad/cobertura/sello ya calculados intactos y su cadena/revocación en sus valores `NOT_CHECKED`/`notChecked()` por defecto, añadiendo una nota a `SignatureReport#anomaly()` (fusionada con cualquier anomalía que el propio `SignatureVerifier` ya hubiera informado, por ejemplo un certificado que no se pudo mapear) — el resto de firmas y el resto del informe no se ven afectados.

`HashCalculator#hash` es la única sección deliberadamente **sin** esta guarda: calcular un hash de un array de bytes no puede fallar de forma significativa con ninguna de las implementaciones de este proyecto, y `PdfAnalysisReport` exige hashes no nulos, así que no hay ningún valor de repuesto razonable que sustituir si de algún modo fallara.

**(T08b) Un resultado vacío nunca debe ser indistinguible de un fallo silencioso**: antes de esta tarea, si `SignatureVerifier#verify` lanzaba una excepción inesperada, el informe degradaba a una lista de firmas vacía -- exactamente igual que un documento legítimamente sin firmar. Ahora, además de degradar con elegancia (comportamiento sin cambios), tanto ese caso como el de `PdfaConformanceValidator#validate` añaden un `SectionError` explícito a `PdfAnalysisReport#sectionErrors()`, identificando qué sección (`SIGNATURES` o `PDFA`) falló y por qué. **(T08b) Orden de la validación PDF/A**: la declaración XMP ahora se comprueba *antes* de invocar el validador formal, en vez de después; un documento que declara PDF/A-2/3 ya no llama en absoluto a *preflight* (cuyo resultado se iba a descartar de todos modos), evitando pagar el coste de un segundo parseo completo del módulo -- ya documentado en otro sitio como pesado -- para un resultado que nunca se iba a usar.

**(T11) Veredicto final**: una vez enriquecidas todas las firmas (cadena + revocación), `verifySignatures` hace una última pasada con `SignatureVerdictPolicy.evaluateAll(...)` sobre la lista completa -- necesita verlas todas juntas para la regla de "cubierta por una firma posterior" (§2.13) -- antes de devolverla. `PdfAnalysisReport.overallVerdict()`/`modifiedAfterLastSignature()` se calculan bajo demanda a partir de esa lista ya enriquecida, no se calculan ni se guardan aparte en `analyze(...)`.

**Tests**: `AnalyzePdfUseCaseTest` (con *fakes* escritos a mano para cada puerto, sin Mockito) cubre la orquestación completa, las tres combinaciones de `validationTime`, el flag de revocación activado/desactivado (incluida una firma sin cadena), la declaración PDF/A-2 → `NOT_VALIDATED`, el aislamiento de fallos por sección (PDF/A, firmas, enriquecimiento de una firma sin afectar a las demás, fusión de anomalías), la propagación de `EncryptedPdfException`/`InvalidPdfException`, y `analyzedAt` viniendo del `Clock` inyectado. `AnalyzePdfUseCaseIntegrationTest` (1) cablea los adaptadores reales (sin *fakes*) contra un PDF firmado y sellado en tiempo real (`TestPdfSigner#signWithTimestamp`) con un almacén de confianza que contiene la raíz de prueba usada para firmar, comprobando un informe completo y coherente: integridad íntegra, cadena de confianza `TRUSTED`, sello de tiempo válido.

### 2.10 Arquitectura hexagonal comprobada con ArchUnit (T08)

`src/test/java/.../architecture/ArchitectureTest` sustituye los `grep` manuales que hasta ahora demostraban (tarea a tarea, en la evidencia de este mismo documento) que el dominio no depende de ninguna librería, por una comprobación automática que se ejecuta en cada `./mvnw verify`:

- **`infrastructure` nunca depende de `application` ni de `api`**: los adaptadores implementan puertos del dominio; no deben conocer quién los usa.
- **`api` (aún no existe, T09) solo podrá depender de `application` y `domain`**: la regla usa `allowEmptyShould(true)` para pasar hoy sin ese paquete y empezar a exigirse en cuanto exista.
- **Sin ciclos de importación entre los cuatro paquetes de primer nivel** (`domain`, `application`, `infrastructure`, `api`).

La importación de clases excluye explícitamente los propios tests (`ImportOption.Predefined.DO_NOT_INCLUDE_TESTS`): los *fixtures* de prueba (`TestPdfFactory`, `TestPki`, etc.) usan PDFBox/Bouncy Castle directamente a propósito y no deben hacer fallar estas reglas, que protegen la arquitectura de producción, no las herramientas de test.

### 2.11 API REST y cableado Spring (T09)

**Endpoint único**: `POST /api/v1/pdf/analyze` (`api/PdfAnalysisController`), `multipart/form-data` con el campo `file` y el parámetro opcional `checkRevocation` (booleano, por defecto `false`). Nunca confía en el nombre del fichero subido: comprueba los propios bytes en busca de una cabecera `%PDF-` reconocible en los primeros 1024 bytes (la misma ventana que usa `PdfBoxDocumentReader`) antes de intentar analizarlo, así que un fichero llamado `factura.pdf` con contenido que no sea un PDF se rechaza igual.

**DTOs explícitos, nunca tipos de dominio en la respuesta** (`api/dto/`): `PdfAnalysisReportMapper` traduce `PdfAnalysisReport` (y todo lo que contiene) a `PdfAnalysisReportDto`, campo a campo, con nombres de campo JSON estables y documentados (`camelCase`). Los enumerados del dominio (`IntegrityStatus`, `ChainStatus`, `RevocationState`, `PdfaValidationStatus`, `Rotation`, `Orientation`, `AnalysisSection`) se exponen como su nombre en texto (`"INTACT"`, `"TRUSTED"`, ...), nunca como el tipo Java. Un `CertificateInfo` **nunca** expone su codificación DER (`encoded`) en la respuesta: en su lugar se calcula y expone una huella SHA-256 (`sha256Fingerprint`) como identificador estable y compacto.

**Validación y errores** (`api/error/`, `@RestControllerAdvice(assignableTypes = PdfAnalysisController.class)`, RFC 9457 `ProblemDetail`):

| Estado | Causa | `type` |
|---|---|---|
| `400` | Falta el campo `file`, o está vacío | `urn:pdfvalidator:error:missing-file` |
| `400` | El contenido no empieza por una cabecera `%PDF-` reconocible (aunque el nombre del fichero termine en `.pdf`) | `urn:pdfvalidator:error:not-a-pdf` |
| `422` | Cabecera `%PDF-` presente, pero el documento está corrupto (`InvalidPdfException`) | `urn:pdfvalidator:error:corrupt-pdf` |
| `422` | El documento está cifrado con una contraseña de usuario no vacía (`EncryptedPdfException`) | `urn:pdfvalidator:error:encrypted-pdf` |
| `413` | El fichero supera el límite de subida configurado (`spring.servlet.multipart.max-file-size`, 80 MB) | `urn:pdfvalidator:error:file-too-large` |
| `503` | Todos los huecos de análisis simultáneo están ocupados tras esperar `acquire-timeout`; lleva la cabecera `Retry-After` (segundos) | `urn:pdfvalidator:error:busy` |
| `500` | Fallo inesperado; nunca se filtra el mensaje de la excepción ni la traza | `urn:pdfvalidator:error:internal-error` |

**Lección aprendida ejecutando la aplicación en local**: `@RestControllerAdvice` sin `assignableTypes` se aplica a **toda** la aplicación, incluido el manejo de errores interno de Spring MVC para peticiones que no llegan a ningún controlador propio. La primera versión de este *advice* no estaba acotada, y su `@ExceptionHandler(Exception.class)` interceptaba la `NoResourceFoundException` que Spring lanza para un endpoint de Actuator no expuesto (p. ej. `/actuator/env`), convirtiendo un `404` correcto en un `500` que además filtraba un mensaje genérico. Se detectó arrancando la aplicación en local y probando `/actuator/env` manualmente (no solo con MockMvc), y se corrigió acotando el *advice* únicamente a `PdfAnalysisController` (`assignableTypes = PdfAnalysisController.class`); un test de regresión (`PdfAnalysisEndToEndTest#healthAndInfoAreExposedButOtherActuatorEndpointsAreNot`) comprueba que Actuator, *springdoc* y el resto de la aplicación siguen con el comportamiento de error por defecto de Spring Boot.

**(T09b) El `413` necesitaba su propio *advice*, sin acotar**: al ejecutar la aplicación en local con un fichero de más de 20 MB se observó un `413` con **cuerpo vacío**, no el `ProblemDetail` esperado. La causa: `DispatcherServlet#doDispatch` resuelve la petición multipart (`checkMultipart`) **antes** de buscar el controlador al que se dirige la petición, así que `MaxUploadSizeExceededException` siempre se lanza sin que Spring haya resuelto todavía ningún *handler* — y un `@ExceptionHandler` acotado con `assignableTypes = PdfAnalysisController.class` (como `PdfAnalysisExceptionHandler`, deliberadamente, para no repetir el error del párrafo anterior) nunca llega a verla. Se añadió un segundo *advice*, `api/error/MaxUploadSizeExceptionHandler`, sin acotar pero que **solo** reacciona a esa única excepción (nunca disparada por Actuator ni por ningún otro endpoint), así que no puede repetir el problema del `404` de más arriba. Probado con un servidor embebido real (`webEnvironment = RANDOM_PORT` + una petición HTTP real con el límite de subida rebajado a 1 KB en la propiedad de test): `MockMvc` no sirve para este caso, porque no aplica el límite de tamaño de un contenedor de servlets real (confirmado empíricamente: la misma petición a través de `MockMvc` devolvía `400`, nunca `413`).

**(T09b) `SectionError` y las anomalías de firma nunca reflejan el mensaje bruto de una excepción**: `AnalyzePdfUseCase` guardaba antes el propio mensaje de la excepción inesperada dentro del `SectionError`/`anomaly` que acaba en la respuesta JSON. Ahora cada guarda registra el detalle real por log (`System.Logger`, servidor) y expone al cliente un texto fijo y estable (p. ej. *"PDF/A-1b validation failed unexpectedly"*, *"signature verification failed unexpectedly"*, *"chain/revocation enrichment failed unexpectedly"*).

**(T09b) Un `IOException` leyendo el fichero subido no es "fichero ausente"**: `PdfAnalysisController` distinguía mal un `IOException` de `MultipartFile#getBytes()` (un fallo leyendo el almacenamiento temporal multipart del propio servidor) de un fichero realmente ausente o vacío — ambos se mapeaban a `400 missing-file`, y además el mensaje de la excepción se filtraba tal cual. Ahora ese caso se informa como `500` (un fallo del servidor leyendo sus propios datos temporales, no un problema de la petición del cliente), sin filtrar el mensaje de la excepción.

**Cableado de adaptadores** (`infrastructure/config/AdapterConfiguration` + `com.coam.pdfvalidator.UseCaseConfiguration`): `AdapterConfiguration` declara un `@Bean` de Spring por cada adaptador de infraestructura (`JcaHashCalculator`, `PdfBoxDocumentReader`, `BcSignatureVerifier`, `PreflightPdfaValidator`, `PkixCertificateChainValidator`, `TrustAnchorProvider`) sin que ninguno de ellos deje de ser una clase Java sencilla e inyectable por constructor. `AnalyzePdfUseCase` (y el `NoOpRevocationChecker` provisional) se cablean, en cambio, en `UseCaseConfiguration`, en el paquete raíz `com.coam.pdfvalidator` -- **fuera** de las cuatro capas de la arquitectura hexagonal -- porque `ArchitectureTest` prohíbe que `infrastructure` dependa de `application`, y el cableado del caso de uso necesariamente depende de ambos. Poner ese único `@Bean` en el paquete raíz (el mismo donde ya vive `PdfValidatorApplication`) es la "raíz de composición" convencional de una arquitectura hexagonal: el pegamento de cableado no pertenece a ninguna de las capas que conecta. La regla de ArchUnit `apiDependsOnlyOnApplicationAndDomain` se amplió en la misma tarea para permitir que `api` dependa también de Spring MVC y de las anotaciones de *springdoc*/*swagger* (indispensables para que exista un controlador REST real), sin dejar de prohibir que dependa de `infrastructure`.

**`TrustStoreProperties`** (`infrastructure/config`, `@ConfigurationProperties(prefix = "pdfvalidator.truststore")`): `external-dir`, `pkcs12-path`, `pkcs12-password`, los tres opcionales (ver §4).

**Documentación OpenAPI** (`infrastructure/config/OpenApiConfiguration`): título, descripción y licencia GPL-3.0; la versión se lee de `BuildProperties` (generado por el objetivo `build-info` de `spring-boot-maven-plugin`, añadido en esta tarea) cuando está disponible, con una constante de respaldo sincronizada manualmente con `pom.xml` para cuando no lo está (p. ej. un `mvn test` suelto, sin pasar por `package`/`verify`).

**Tests**: `PdfAnalysisControllerTest` (slice `@WebMvcTest`, caso de uso *stubbeado* con `@MockitoBean`): 200 con el informe mapeado, `checkRevocation` reenviado (y su valor por defecto `false`), 400 (fichero ausente/vacío, contenido sin cabecera PDF), 422 (corrupto, cifrado), 500 sin filtrar el mensaje, y **(T09b)** un `IOException` leyendo el fichero subido mapeado a `500`, no a `400`. `PdfAnalysisExceptionHandlerTest`: cada `@ExceptionHandler` probado directamente (sin contexto Spring), incluida la comprobación de que el detalle de un fallo inesperado no contiene el mensaje original de la excepción. **(T09b)** `MaxUploadSizeExceptionHandlerTest` (el `@ExceptionHandler` en sí, invocado directamente) y `MaxUploadSizeExceptionHandlerIntegrationTest` (`@SpringBootTest` con `webEnvironment = RANDOM_PORT`, límite de subida rebajado a 1 KB por propiedad de test, petición HTTP real): confirman que el `413` real ya lleva cuerpo `ProblemDetail`. `PdfAnalysisReportMapperTest`: mapeo campo a campo de un informe completo, incluida la comprobación estructural (por reflexión) de que `CertificateInfoDto` no tiene ningún componente de tipo `byte[]`. `PdfAnalysisEndToEndTest` (`@SpringBootTest` + `MockMvc`, un único test de extremo a extremo con adaptadores reales): sube un PDF firmado y sellado en tiempo real (`TestPdfFactory#signedWithTimestamp`) y comprueba el JSON completo; además sirve de test de "el contexto arranca" para `/v3/api-docs` (contiene la ruta `/api/v1/pdf/analyze`, título y licencia correctos) y para la exposición de Actuator (`health`/`info` sí, el resto no).

### 2.12 Comprobación de revocación OCSP/CRL (T10)

`infrastructure/revocation/CompositeRevocationChecker` implementa el puerto `RevocationChecker`: OCSP primero, CRL como respaldo cuando OCSP no está disponible o no es concluyente. Es una función **opcional, acotada y de mejor esfuerzo** — nunca bloquea ni hace fallar el resto del análisis.

**Orden y semántica**:

1. Si el certificado no declara ninguna URL OCSP ni CRL (extensiones AIA/CDP), o el emisor no está disponible → `UNKNOWN`.
2. Se intenta OCSP contra cada URL declarada, en orden, hasta obtener un resultado concluyente (`GOOD`/`REVOKED`) o agotar la lista.
3. Si OCSP no fue concluyente y hay al menos una URL CRL, se intenta CRL de la misma forma.
4. Si ninguno de los dos fue concluyente, el resultado final es `UNKNOWN` con un motivo que combina ambos intentos (p. ej. `"OCSP: ...; CRL: ..."`).
5. Cualquier fallo de red, protocolo o verificación criptográfica se traduce siempre a `UNKNOWN` con un motivo estable y no sensible — nunca se lanza una excepción, y nunca se filtra el detalle interno de la excepción real (se registra por log).

**Timeout estricto (2 s por defecto) y límite de tamaño de respuesta (10 MB por defecto)**, ambos configurables (`pdfvalidator.revocation.*`, §4) y aplicados independientemente a cada petición OCSP/CRL.

**Verificación real, no solo "se recibió una respuesta"**:

- **OCSP** (`infrastructure/revocation/OcspClient`, RFC 6960): construye la petición con Bouncy Castle (`OCSPReqBuilder`, `JcaCertificateID`, extensión *nonce* aleatoria de 16 bytes para detectar una respuesta repetida/*replay*), la envía por POST (`application/ocsp-request`), y antes de confiar en el veredicto comprueba: que el respondedor sea el propio emisor o un respondedor delegado emitido por el emisor con el uso extendido de clave `id-kp-OCSPSigning`; que la firma de la respuesta verifique contra la clave pública correspondiente; que el `CertID` de la respuesta coincida con el de la petición; frescura de `thisUpdate`/`nextUpdate` (con un margen de reloj de 5 minutos); y que el *nonce*, si el respondedor lo devuelve, coincida con el enviado.
- **CRL** (`infrastructure/revocation/CrlClient`, RFC 5280): descarga la lista (GET), la parsea con `java.security.cert.CertificateFactory` (sin necesidad de Bouncy Castle para esta parte), verifica su firma contra la clave pública del emisor, comprueba que no esté caducada (`nextUpdate` con el mismo margen de 5 minutos), y busca el número de serie del certificado entre las entradas revocadas.

**Guarda SSRF con conexión anclada (*pinned*), no solo un filtro de URL**: las URLs OCSP/CRL vienen de extensiones de un certificado — potencialmente hostil — así que antes de contactar nada, `RevocationUrlGuard`:

- Solo acepta `http` (nunca `https` — ver más abajo).
- Resuelve el nombre de host **una sola vez** y descarta cualquier dirección privada/reservada a menos que sea una excepción explícita de test: *loopback*, enlace local (incluida la dirección de metadatos de nube `169.254.169.254`), RFC 1918 (`10/8`, `172.16/12`, `192.168/16`), `0.0.0.0/8`, CGNAT (`100.64.0.0/10`), multidifusión, IPv6 *unique-local* (`fc00::/7`) — también cuando vienen disfrazadas como una dirección IPv4 mapeada en IPv6 (`::ffff:10.0.0.1`).
- **Por qué resolver una sola vez importa (DNS rebinding)**: una primera versión de esta guarda resolvía el nombre para validarlo y dejaba que el cliente HTTP lo resolviera *otra vez* al conectar — un servidor DNS autoritativo hostil puede responder a esas dos resoluciones de forma distinta (una dirección pública para la comprobación, una privada para la conexión real), sorteando la guarda por completo. La solución no es solo un mejor filtro: `RevocationUrlGuard#resolve` resuelve el host una única vez, elige una dirección permitida, y devuelve esa dirección exacta junto con la URI (`ValidatedTarget`); `PinnedHttpClient` conecta un `Socket` directamente a esa dirección — nunca vuelve a resolver el nombre.
- `PinnedHttpClient` es un cliente HTTP/1.1 mínimo construido a propósito sobre `java.net.Socket`, no sobre `java.net.http.HttpClient`: este último no ofrece ninguna forma pública de fijar la dirección resuelta de una petición en esta versión del JDK, así que no puede cerrar el hueco de *DNS rebinding* anterior. Nunca sigue redirecciones (no hay código de redirección en absoluto).
- **Por qué solo `http`, nunca `https`**: anclar la conexión a una dirección IP concreta mientras se mantiene la verificación TLS (SNI + verificación de nombre de host) contra el nombre *original* es técnicamente posible (`SSLSocketFactory#createSocket(Socket, String, int, boolean)`), pero se consideró desproporcionado para el alcance de esta tarea — la comprobación de revocación es opcional, de mejor esfuerzo y ya acotada a un par de segundos. Una URL `https://` en AIA/CDP se rechaza con un motivo `UNKNOWN` explícito en vez de una implementación TLS fragil o parcialmente correcta. Las dos entidades reales usadas para verificación manual en este proyecto (FNMT, Camerfirma) publican OCSP/CRL por `http://` — práctica habitual en las CA (la confianza la aporta la respuesta firmada, no el transporte).
- El guardián de direcciones privadas solo se desactiva mediante un constructor de solo-test (nunca alcanzable desde el cableado de producción), usado para apuntar a un servidor HTTP local durante los tests.

**Puerta de confianza: la revocación solo se comprueba para una cadena `TRUSTED`** (decisión de seguridad, §2.9/§10): las URLs OCSP/CRL viven dentro de certificados firmados por la propia CA emisora — para una cadena `TRUSTED` esos certificados los escribió una CA real y de confianza, no quien subió el documento, lo que cierra el vector principal de SSRF (un certificado autofirmado y fabricado a mano con una URL OCSP interna nunca llega a `TRUSTED`). Además, el certificado y el emisor que se le pasan al `RevocationChecker` se toman de `CertificateChainValidator#validatedPath` — los certificados que PKIX realmente usó para construir esa ruta de confianza —, nunca directamente de la cadena que extrajo `SignatureVerifier` del CMS: un CMS hostil podría embeber un certificado adicional, irrelevante para la ruta de confianza real, junto a una cadena por lo demás genuina, y ese certificado adicional nunca debe consultarse. La guarda de red (anclaje SSRF de arriba) se mantiene como defensa en profundidad, no en sustitución de esta puerta.

**No es una validación completa contra la Lista de Confianza europea (TSL/EU LOTL)**: al igual que §2.7, esto comprueba OCSP/CRL contra el emisor tal y como aparece en el propio certificado, no contra un catálogo de servicios de confianza publicados por la UE con su estado y periodo de vigencia oficial — ver la tarea futura T14.

**Tests**: `RevocationUrlGuardTest` (URLs válidas/no válidas, cada rango de direcciones privadas/reservadas rechazado, `https` rechazado, resolución única incluso con varias direcciones candidatas), `OcspClientTest`/`CrlClientTest` (contra un servidor HTTP real de test — ver más abajo — con respuestas OCSP/CRL reales y firmadas: `GOOD`, `REVOKED`, estado desconocido, firma inválida, *timeout*, CRL caducada, error HTTP, sin URL, y la prueba explícita de que la conexión va a la dirección anclada de una única resolución), `CompositeRevocationCheckerTest` (orden OCSP→CRL, sin URLs, emisor `null`), `AnalyzePdfUseCaseTest` (la puerta de confianza: `UNTRUSTED_ROOT`/`INCOMPLETE_CHAIN`/`EXPIRED` → `NOT_CHECKED` sin invocar al *checker*; `TRUSTED` → invocado; se usa `validatedPath`, no la cadena presentada, cuando difieren), `PkixCertificateChainValidatorTest` (`validatedPath` reconstruye la ruta real, incluida la certificación de anclaje cuando el ancla no viene en el CMS, y **excluye** un certificado adicional no relacionado presentado junto a una ruta genuina).

**Elección del servidor HTTP de test**: en vez de WireMock (`org.wiremock:wiremock-standalone`), estos tests usan `com.sun.net.httpserver.HttpServer` (incluido en el JDK, sin dependencia nueva) — decisión tomada para eliminar cualquier riesgo de conflicto de classpath entre el Jetty embebido de WireMock y el propio arranque de Jetty/Spring Boot 4.1.1, sin necesidad de resolverlo empíricamente primero.

### 2.13 Veredicto general por firma e interfaz web "Validar" (T11)

**`domain/policy/SignatureVerdictPolicy`** (política de dominio pura, sin librerías) combina `IntegrityStatus`, `ChainStatus` y `RevocationStatus` de cada firma ya enriquecida en un único `SignatureVerdict`, más un `OverallVerdict` a nivel de documento (§2.3), según esta tabla de decisión (evaluada de arriba a abajo; la primera fila que aplica decide):

| Condición | Veredicto | Motivo (`verdictReasons`) |
|---|---|---|
| `INVALID_SIGNATURE` | ❌ `INVALID` | `SIGNATURE_INVALID` |
| `UNSUPPORTED` (subfiltro no soportado) | ⚠️ `NOT_ADMITTED` | `SIGNATURE_FORMAT_UNSUPPORTED` |
| `MODIFIED_AFTER_SIGNING`, no existe ninguna firma posterior en el documento | ❌ `INVALID` | `MODIFIED_AFTER_LAST_SIGNATURE` |
| `MODIFIED_AFTER_SIGNING`, existe alguna firma posterior pero **no todas** están admitidas (veredicto `VALID` completo) **(T11c, ver salvedad de seguridad abajo)** | ❌ `INVALID` | `MODIFIED_AFTER_SIGNING_BY_UNADMITTED_PARTY` |
| `MODIFIED_AFTER_SIGNING`, existe al menos una firma posterior y **todas** están admitidas | *(continúa con cadena/revocación de abajo)* | `COVERED_BY_LATER_SIGNATURE` (informativo) |
| Integra, cadena `UNTRUSTED_ROOT` / `INCOMPLETE_CHAIN` / `EXPIRED` / `NOT_CHECKED` | ⚠️ `NOT_ADMITTED` | `CHAIN_UNTRUSTED_ROOT` / `CHAIN_INCOMPLETE` / `CHAIN_EXPIRED` / `CHAIN_NOT_CHECKED` |
| Cadena `TRUSTED`, revocación no solicitada en esta petición | ✅ `VALID` | `REVOCATION_NOT_REQUESTED` (informativo -- la interfaz debe decir "revocación no comprobada", nunca dar a entender que sí se comprobó) |
| Cadena `TRUSTED`, revocación solicitada, `GOOD` | ✅ `VALID` | — |
| Cadena `TRUSTED`, revocación solicitada, `REVOKED` | ❌ `INVALID` | `REVOCATION_REVOKED` |
| Cadena `TRUSTED`, revocación solicitada, `UNKNOWN` | ⚠️ `NOT_ADMITTED` | `REVOCATION_UNKNOWN` |
| Cadena `TRUSTED`, revocación solicitada, sigue en `NOT_CHECKED` (p. ej. el caso límite de ruta validada vacía, T10b) | ⚠️ `NOT_ADMITTED` | `REVOCATION_UNAVAILABLE` |

`OverallVerdict` (documento) es el peor de los veredictos anteriores (`INVALID` > `NOT_ADMITTED` > `VALID`), `NO_SIGNATURES` si el documento no tiene ninguna firma, o **(T11c)** `ANALYSIS_INCOMPLETE` cuando la propia sección `SIGNATURES` falló de forma inesperada (`sectionErrors`, §2.9) -- una lista de firmas vacía causada por ese fallo nunca debe confundirse con "el documento legítimamente no está firmado"; la interfaz lo muestra como "No se ha podido completar el análisis de firmas".

**Decisiones explícitas**:

- **`UNSUPPORTED` es `NOT_ADMITTED`, no `INVALID`.** Un subfiltro no reconocido significa que este servicio no pudo verificar la firma en ningún sentido -- no es una prueba de que la firma esté mal, así que tratarlo igual que una firma criptográficamente rota exageraría lo que realmente se sabe.
- **`REVOKED` es siempre `INVALID`** (decisión explícita del usuario). *Salvedad, también en la interfaz*: este servicio consulta el estado de revocación **actual** vía OCSP/CRL (§2.12), no una comprobación en el instante concreto de la firma -- un certificado revocado después de firmar válidamente seguirá apareciendo aquí como `REVOKED`.
- **Regla de varias firmas (T11c: corregida por seguridad)**: una firma anterior con `MODIFIED_AFTER_SIGNING` solo se exime de la penalización cuando **todas** las firmas posteriores del documento están ellas mismas **admitidas** (un veredicto `VALID` completo -- cadena de confianza y, si se solicitó, revocación), no basta con que sean `INTACT`. **Vulnerabilidad cerrada**: antes de esta corrección, bastaba con que *alguna* firma posterior fuera `INTACT` y cubriera el fichero completo, sin importar si esa firma posterior era de confianza. Esto permitía el siguiente ataque: un atacante modifica un documento firmado por una entidad de confianza y lo vuelve a firmar con un certificado autofirmado hecho por él mismo; como esa firma del atacante cubre el fichero hasta el final e `IntegrityStatus.INTACT` solo exige que el CMS verifique (no que el certificado sea de confianza), la firma original -- ya modificada -- seguía apareciendo como ✅ `VALID`. Exigir que **cada** firma posterior esté admitida corrige esto: solo un firmante en el que este servicio realmente confía puede dar fe de la revisión añadida; de lo contrario, la firma anterior es ❌ `INVALID` con el motivo `MODIFIED_AFTER_SIGNING_BY_UNADMITTED_PARTY`. Sigue siendo una comprobación **estructural** (el `ByteRange` de cada firma posterior llega al final real del fichero, su CMS verificó, y además su cadena/revocación son de confianza), **no** una comparación del contenido añadido entre revisiones -- ver la limitación siguiente. `PdfAnalysisReport.modifiedAfterLastSignature()` expone el mismo hecho estructural a nivel de documento (sin el requisito de admisión), independientemente del resultado de confianza de esa última firma: es cierto en cuanto **ninguna** firma alcanza el final real del fichero, incluso si esa última firma es en sí misma `INVALID_SIGNATURE` (dos problemas distintos, ambos visibles).
- **Limitación documentada**: no se comparan los bytes concretos que una revisión incremental añadió; "cubierta por una firma posterior admitida" es una garantía estructural más una comprobación de confianza, no una prueba de que el contenido visible no cambió entre esa firma y la última.

**Interfaz web "Validar"** (`src/main/resources/static/`, sin *build step*, sin *frameworks*, sin CDNs -- JavaScript nativo con módulos ES, HTML y CSS servidos tal cual por Spring Boot):

- **Cómo abrirla**: con la aplicación arrancada (§4), `http://localhost:8963/` (o `/index.html`).
- **Qué muestra**: zona de arrastrar-y-soltar (o clic para seleccionar) para un PDF de hasta 80 MB, una casilla "Comprobar revocación (OCSP/CRL)", y un botón "Analizar PDF" que llama a `POST /api/v1/pdf/analyze`. El resultado muestra, en este orden: un **banner de veredicto general** (✅ *Firma válida* / ⚠️ *Firma no admitida* / ❌ *Firma inválida* / *Documento sin firmas* / **(T11c)** ⚠️ *Análisis incompleto*, "No se ha podido completar el análisis de firmas") con sus motivos en español llano; una tarjeta por firma (firmante, emisor, fecha declarada, sello de tiempo, integridad, cadena, revocación, motivos del veredicto, anomalías) con un desplegable de detalles técnicos (cadena completa con huellas SHA-256, cobertura del `ByteRange`); una sección de documento (hashes con botón de copiar, versión, tabla de páginas con rotación/orientación/tamaño, cifrado y permisos, resultado PDF/A con sus incidencias); los `sectionErrors`, si los hay, como avisos; y un botón para descargar el informe JSON completo. Los códigos de motivo (`CHAIN_EXPIRED`, `REVOCATION_UNKNOWN`, ...) se traducen a texto en español en el propio `app.js` (`REASON_TEXT`), nunca en el backend -- el backend solo expone códigos estables.
- **Tema claro/oscuro**: variables CSS (`prefers-color-scheme` del sistema, más un botón manual que persiste la elección en `localStorage`, envuelto en `try`/`catch` por si el almacenamiento no está disponible).
- **Navegación**: pestaña "Firmar" visible pero deshabilitada ("próximamente") -- reservada para T11b (AutoFirma).
- **Accesibilidad**: HTML semántico, región de arrastrar-y-soltar operable por teclado (`tabindex`, `Enter`/`Espacio`), regiones `aria-live` para carga/errores/resultados, ningún estado se transmite solo por color (siempre icono + texto), contraste suficiente en ambos temas -- **(T11c)** el color de texto tenue (`--color-text-faint`) se subió a un contraste WCAG AA ≥ 4.5:1 sobre su fondo en ambos temas (el valor original quedaba por debajo del umbral), y de paso se corrigió un valor hexadecimal inválido de 7 dígitos (`#8890999`) que había quedado en el tema claro sin que ningún navegador lo avisara en pantalla (solo lo detecta un linter/lector de CSS estricto).
- **Robustez de la interfaz (T11c)**: un segundo `submit` mientras ya hay una petición en curso (doble clic, `Enter` mantenido, un evento sintético) se ignora -- un único `AbortController` en `inFlightAnalysis` sirve a la vez de bandera "hay petición en curso" y de forma de cancelarla si hiciera falta; la zona de arrastrar-y-soltar y el selector de fichero quedan igualmente bloqueados mientras tanto. Una respuesta `2xx` cuyo JSON no tiene la forma esperada (`isValidReportPayload`: comprueba `overallVerdict`, `signatures`, `hashes`, `structure`, `security`, `pdfa`) muestra un error en español en vez de dejar que los renderizadores lancen una excepción sobre un campo ausente. Seleccionar un fichero inválido (no PDF, o que supera 20 MB) después de tener uno válido ya seleccionado limpia la selección anterior y la miniatura (`clearSelectedFile`) en vez de dejar la selección antigua activa mientras la interfaz muestra el nombre del fichero rechazado.
- **Seguridad**: toda cadena que pueda venir del PDF analizado (nombre de firmante, nombre de campo, motivo de anomalía, ...) se renderiza con `textContent`, nunca `innerHTML` -- el único uso de `innerHTML` en `app.js` es una tabla fija de iconos SVG escrita por el propio desarrollador, nunca datos del servidor (documentado en el propio código, verificado con `grep -n innerHTML`). Un filtro Spring (`infrastructure/web/CspHeaderFilter`, registrado ampliamente pero que solo añade la cabecera para las rutas exactas `/`, `/index.html`, `/app.js`, `/styles.css`) añade `Content-Security-Policy: default-src 'self'; img-src 'self' data:; style-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'`, sin afectar a Swagger UI, Actuator ni al propio endpoint de análisis (probado con un test de Spring MVC, `StaticContentSecurityTest`, incluida una comprobación negativa dedicada sobre `/api/v1/pdf/analyze`). **(T11c)** El filtro compara la ruta relativa al *context path* (`request.getRequestURI()` menos `request.getContextPath()`), no `getRequestURI()` tal cual -- `getRequestURI()` ya incluye el *context path*, así que la comparación original dejaba de proteger la interfaz estática en cuanto la aplicación se desplegara bajo uno (p. ej. `/pdfvalidator/app.js` nunca coincidía con `/app.js`); probado con `CspHeaderFilterTest` (test unitario directo sobre el filtro, sin `MockMvc`, que siempre arranca con *context path* vacío) tanto sin *context path* como con uno.
- **Bug real encontrado en la verificación manual**: en la primera versión, elementos con el atributo `hidden` (la miniatura del fichero, el banner de error, el *spinner* de carga) seguían visibles al cargar la página, porque reglas posteriores de la misma hoja de estilos (`.file-chip { display: inline-flex }`, `.error-banner { display: flex }`, la regla compartida `svg { display: block }`) tienen la misma especificidad CSS que el `[hidden] { display: none }` por defecto del navegador y, al ir después en la cascada, ganaban. Corregido con una única regla `[hidden] { display: none !important; }` cerca del principio de `styles.css`.
- **Ortografía en español y codificación UTF-8**: todo el texto en español visible de `index.html`/`app.js` lleva tildes, `ñ` y `¿`/`¡` correctos (por ejemplo, "Firma válida"/"Firma inválida", "revocación", "electrónica", diferenciando además pares que cambian de significado según el acento, como "válida"/"valida" o "Sí"/"si"); `index.html` declara `<meta charset="utf-8">` como primer elemento de `<head>` y `<html lang="es">`, y ambos ficheros se guardan en UTF-8 sin BOM. `CspHeaderFilter` (mismo filtro, mismos cuatro *paths* exactos que ya llevaban la cabecera CSP) también fuerza `response.setCharacterEncoding("UTF-8")` antes de que el manejador de recursos estáticos fije el `Content-Type`, así que `/`, `/index.html`, `/app.js` y `/styles.css` se sirven con `charset=UTF-8` explícito -- verificado con `curl -I`. Se probó primero la propiedad global `spring.servlet.encoding.force=true` (en Spring Boot 4 el prefijo cambió de `server.servlet.encoding.*` a `spring.servlet.encoding.*`), pero se descartó: fuerza el *charset* también en las respuestas JSON de la API, y `PdfAnalysisControllerTest` espera `Content-Type: application/json` sin parámetro de *charset*; de ahí que la solución final reutilice el filtro ya acotado a los cuatro *paths* estáticos en vez de una propiedad global.
- **Tests**: `SignatureVerdictPolicyTest` (todas las filas de la tabla, más los casos de varias firmas, incluida **(T11c)** la regla de cobertura por firma posterior admitida); `PdfAnalysisReportMapperTest`/`PdfAnalysisControllerTest` (forma del JSON: `verdict`/`verdictReasons` por firma, `overallVerdict`/`modifiedAfterLastSignature` del documento, incluido un documento sin firmar → `NO_SIGNATURES`); `AnalyzePdfUseCaseTest` **(T11c)** (un fallo inesperado de la sección de firmas produce `overallVerdict` `ANALYSIS_INCOMPLETE`, no `NO_SIGNATURES`); `StaticContentSecurityTest` (cabecera CSP presente en `/`, `/index.html`, `/app.js`, `/styles.css`, ausente en `/v3/api-docs` **y (T11c)** en `/api/v1/pdf/analyze`); `CspHeaderFilterTest` **(T11c)** (el filtro probado directamente, sin y con *context path*). La interfaz en sí (HTML/CSS/JS) se verificó manualmente en un navegador real (Chrome, vía Chrome DevTools) en modo claro y oscuro, con un PDF firmado real generado por `TestPdfFactory` **(T11c: además, doble `submit` → una sola petición `fetch`; payload `2xx` con forma inválida → banner de error en español; selección de fichero inválido tras uno válido → limpia la selección)**, sin ningún test JS automatizado (decisión permitida por el propio alcance de la tarea).

### 2.14 Pantalla "Firmar" con AutoFirma (T11b)

Firma un PDF con el propio certificado del usuario (DNIe, FNMT, ...) usando **AutoFirma**, la aplicación de escritorio oficial. Es la misma página que "Validar" (`static/index.html`), con una segunda pestaña habilitada -- se eligió una sola página con pestañas en vez de un `firmar.html` separado precisamente para poder reutilizar sin duplicar la cabecera, el tema, el filtro CSP y, sobre todo, el renderizado del informe (`render.js`) para el botón "Validar este PDF" (ver más abajo).

- **Flujo**: el usuario elige o arrastra un PDF (≤ 80 MB, con doble comprobación en el cliente: extensión/MIME como en "Validar", **y** los 5 primeros bytes del fichero (`%PDF-`) leídos con `file.slice(0,5).arrayBuffer()`, ya que aquí el fichero nunca llega al servidor para que el backend lo compruebe) → se lee como base64 (`FileReader.readAsDataURL`) → `AutoScript.sign(dataB64, "SHA256withRSA", "PAdES", extraParams, onSuccess, onError)` invoca a AutoFirma en el equipo del usuario, que abre su propio selector de certificado → al terminar, AutoFirma devuelve el PDF firmado en base64 → la interfaz ofrece "Descargar PDF firmado" (`Blob` + URL de objeto, revocada tras la descarga, nombre `<original>-firmado.pdf`) y "Validar este PDF", que envía esos mismos bytes a `POST /api/v1/pdf/analyze` **reutilizando literalmente `analyzeFile()` de `validate.js`** (mismo *fetch*, mismo `render.js`, mismo panel de resultados) en vez de duplicar esa lógica.
- **Firma invisible por defecto**; un campo opcional "Motivo de la firma" se traduce a la propiedad `signReason` de AutoScript (confirmada leyendo `PdfExtraParams.SIGN_REASON` en el propio repositorio oficial, `afirma-crypto-pdf-common`), enviada como una cadena con formato Java Properties (`signReason=...\n`), tal y como espera `AutoScript.sign`.
- **Cómo se inicializa AutoScript (verificado leyendo el código fuente 1.10.1, no adivinado)**: `AutoScript.cargarAppAfirma()` se llama **sin** `AutoScript.setForceWSMode(true)`. Ese nombre es engañoso: pese a sonar a "modo WebSocket", fuerza justo lo contrario -- el transporte de **servidor intermedio** (`AppAfirmaJSWebService`, que necesita *servlets* propios de guardado/recuperación, exactamente lo que esta tarea pide evitar). Dejando el flag sin activar, cualquier navegador de escritorio moderno con soporte de WebSocket (todos los soportados por este proyecto) elige automáticamente `AppAfirmaWebSocketClient`, que habla directamente con AutoFirma en `wss://127.0.0.1:<puerto>` -- sin ningún servidor intermedio. `SupportDialog.enableSupportDialog(false)` se llama también antes de inicializar: la librería, si no se desactiva, inyecta su propio diálogo modal de carga/error mediante un elemento `<style>` con estilo *inline* (`document.createElement("style")` + `.innerText`), que una CSP con `style-src 'self'` (sin `'unsafe-inline'`) dejaría sin aplicar sus reglas -- desactivarlo evita ese problema por completo (y de paso evita duplicar la propia interfaz de espera/cancelar de este proyecto).
- **Ningún dato ni fichero pasa por un servidor intermedio de guardado/recuperación**: la clave privada nunca sale del equipo del usuario (la operación criptográfica ocurre enteramente dentro de AutoFirma); este servicio no recibe el PDF sin firmar en ningún momento de este flujo, y solo recibe el PDF firmado si el usuario pulsa "Validar este PDF" explícitamente -- explicado en una sola frase, visible, en la propia pantalla.
- **Estado de espera y errores en español**, verificado directamente contra el código fuente de AutoScript 1.10.1 (`ErrorCode`, no adivinado): mientras AutoFirma responde se muestra "Esperando a AutoFirma... elige tu certificado en la ventana de AutoFirma" con un botón "Cancelar" -- como no existe ninguna API de AutoScript para abortar una operación nativa en curso, "cancelar" aquí significa que esta página deja de esperar (un contador de generación monótono invalida cualquier respuesta tardía de esa operación, que se ignora silenciosamente si AutoFirma acaba respondiendo más tarde). Códigos mapeados a español: cancelado por el usuario (`AOCancelledOperationException`/`AS500001`); AutoFirma no instalado o sin responder tras agotar los reintentos propios de la librería (`ApplicationNotFoundException`/`AS620017`/`AS620020`/`AS620025`, con el enlace oficial de descarga `https://firmaelectronica.gob.es/Home/Descargas.html`); documento no válido (heurística por nombre de excepción, ya que AutoFirma no publica un código específico para esto en esta librería JavaScript); y un motivo genérico que siempre muestra el tipo de excepción y el mensaje reales en vez de ocultarlos, para que un problema no catalogado no deje al usuario sin ninguna pista.
- **CSP**: la política sigue sin `'unsafe-eval'` ni `'unsafe-inline'` para scripts (verificado leyendo el código: AutoScript nunca llama a `eval()`/`Function()`, no genera `<script>` en línea, y se sirve como fichero externo `script-src 'self'`). Se añadieron dos directivas mínimas y justificadas por el propio código de la librería: `connect-src 'self' wss://127.0.0.1:* https://127.0.0.1:*` (el cliente WebSocket habla por `wss://127.0.0.1:<puerto>`; su alternativa de compatibilidad para navegadores antiguos, por `https://127.0.0.1:<puerto>`; el puerto es siempre dinámico, nunca fijo, de ahí el comodín) y `frame-src 'self' afirma:` (el lanzamiento de AutoFirma navega a una URL `afirma://...`; en Chrome/Edge es una redirección de nivel superior no afectada por estas directivas, pero en Firefox/Safari la librería usa un `<iframe>` oculto de 1x1 px, que sin esta entrada quedaría bloqueado por `default-src 'self'`). Probado con `StaticContentSecurityTest`/`CspHeaderFilterTest` (cabecera exacta actualizada) y manualmente con Chrome DevTools: ninguna conexión WebSocket a `127.0.0.1` fue bloqueada por CSP (solo rechazada por el sistema operativo con `net::ERR_CONNECTION_REFUSED`, al no haber ningún proceso de AutoFirma escuchando en esta máquina de desarrollo).
- **Módulos del frontend**: `app.js` quedó como punto de entrada mínimo (tema + pestañas); el resto se dividió en `dom.js` (referencias al DOM y utilidades compartidas: tema, formato, iconos SVG, comprobación de bytes mágicos `%PDF-`, base64↔Blob), `render.js` (todo el renderizado del informe, sin cambios de comportamiento respecto a T11/T11c), `validate.js` (la pantalla "Validar", con `analyzeFile()`/`isAnalyzing()` exportados) y `sign.js` (la pantalla "Firmar"). Refactorización mecánica: mismo comportamiento verificado con `./mvnw verify` (backend) y una verificación manual completa (frontend, no hay *harness* de test JS en este proyecto, §7).
- **Verificación manual (Chrome DevTools MCP, puerto 8081, AutoFirma no instalado en esta máquina)**: pestaña "Firmar" se activa sin errores de consola; un PDF real generado con `TestPdfFactory.signedWithTimestamp()` se selecciona correctamente (comprobación de bytes mágicos asíncrona incluida) y habilita "Firmar PDF"; al pulsar, aparece el estado de espera correcto y, tras agotar los reintentos de AutoScript (~33 s), el mensaje "No se pudo conectar con AutoFirma..." con el enlace de descarga, exactamente el comportamiento esperado sin AutoFirma instalado; el botón "Cancelar" detiene la espera y muestra "Has cancelado la operación de firma."; cambio de pestaña y de tema verificados sin regresiones. **No se intentó una firma real con ningún certificado**, conforme a la instrucción de la tarea. Aplicación detenida al terminar.

### 2.15 Pulido visual y robustez de la firma (T11e)

**Ritmo de espaciado deliberado** (`styles.css`, mismos *tokens* `--space-*` ya existentes, sin ninguno nuevo): el detector de diseño Impeccable señaló un espaciado monótono (un mismo valor pequeño repetido en exceso). Se estableció una cadencia real de varios niveles reutilizando la escala existente -- apretado dentro de un mismo grupo (icono + texto, etiqueta + valor, cabecera de tarjeta), medio entre controles relacionados de un mismo formulario, generoso entre secciones mayores: `panel-subtitle` → zona de arrastre (`--space-5` → `--space-6`), *chip* de fichero pegado a la zona de arrastre (`--space-4` → `--space-3`, mismo grupo "fichero seleccionado"), botón de acción ligeramente más cerca de las opciones que antes (`--space-5` → `--space-4`), separación entre el banner de veredicto y el resto del informe (`--space-5` → `--space-6`), separación entre las columnas "Firmas"/"Documento" (`--space-5` → `--space-6`), y separación entre el panel de formulario y el panel de resultados (`--space-5` → `--space-7`, la transición más generosa de la página, con un valor reducido a `--space-6` en el punto de corte móvil de 640&nbsp;px). Verificado antes/después con `impeccable detect --scope layout`: el hallazgo persistía tras el ajuste (el detector cuenta la frecuencia bruta de los valores más pequeños en toda la hoja de estilos, que siguen siendo mayoría porque de verdad hay muchos grupos apretados legítimos -- iconos junto a texto, bordes, *offsets* de foco); se registró como excepción acotada a `index.html` con `impeccable hooks ignore-value monotonous-spacing "*" --file src/main/resources/static/index.html`, documentando el motivo (falso positivo confiado: existe una cadencia real de varios pasos, no un único valor repetido). Contraste WCAG AA, foco visible y `prefers-reduced-motion` no se tocaron (ya cumplían).
- **Correcciones de robustez en `sign.js`** (avisos de la revisión de T11b):
  - **Respuesta tardía tras cancelar**: ya usaba un contador de generación por intento (`inFlightGeneration`/`nextGeneration`) que ignora cualquier respuesta de AutoFirma que llegue después de un `Cancelar` o de un intento posterior -- verificado de nuevo en el navegador simulando una respuesta tardía tras cancelar y tras iniciar un segundo intento: la respuesta del primer intento no toca el estado del segundo.
  - **"Motivo" con tildes/ñ**: verificado leyendo `Base64.encode`/`_utf8_encode` en el propio `autoscript.js` vendido (sin modificarlo) -- codifica el texto en UTF-8 antes de convertirlo a base64 para cualquier valor de `extraParams`, así que el texto tal cual (sin ningún escapado adicional propio) es lo correcto; probado manualmente con "Revisión técnica — año 2026" enviado a `AutoScript.sign` intacto.
  - **Guarda del `base64` de éxito**: `onSignSuccess` envuelve `base64ToBlob(...)` en un `try`/`catch` -- una respuesta corrupta o no-base64 muestra ahora "AutoFirma devolvió una respuesta que no se pudo interpretar" en vez de lanzar una excepción sin capturar; probado manualmente inyectando una respuesta de éxito con contenido no-base64.
  - **Visibilidad de "Validar este PDF"**: `switchTab` (ahora compartida entre `app.js` y `sign.js` vía `dom.js`, evitando duplicar la lógica de pestañas) cambia a la pestaña "Validar" antes de analizar el PDF firmado, y el foco se mueve a `#results-heading` (ahora con `tabindex="-1"`) con `scrollIntoView` una vez el resultado está listo, respetando `prefers-reduced-motion`; el propio banner de veredicto (`aria-live="polite"`) anuncia el resultado. Probado manualmente en el navegador (éxito → cambia de pestaña, hace *scroll* y mueve el foco; error → el banner de error, ya visible en la pestaña Validar, se anuncia solo con su propio `aria-live="assertive"`, sin mover el foco a un panel que sigue oculto).

### 2.16 DN legible, permisos traducidos, cadena sin desbordamiento y footer neutro (T11f)

Cuatro correcciones de pulido tras una **firma real con AutoFirma** (captura de pantalla del resultado de "Validar"), la primera de ellas también un problema de fondo, no solo de estilo:

- **DN ilegible por el `#16<hex>` de `emailAddress` (backend, TDD)**: `X509CertificateInfoMapper` usaba `X500Principal#getName()` (formato RFC 2253 de la JDK) para `subject`/`issuer`. La JDK solo conoce un puñado de atributos (`CN`, `OU`, `O`, `L`, `ST`, `C`...); cualquier otro, incluido `emailAddress` (OID `1.2.840.113549.1.9.1`, muy habitual en certificados cualificados españoles), se vuelca como `<oid>=#16<hex-DER>` -- ilegible. Corregido formateando el sujeto/emisor con **Bouncy Castle `X500Name` + `BCStyle`** (`BCStyle.INSTANCE.toString(...)`), que reconoce ese y otros atributos (`SERIALNUMBER`, `GIVENNAME`, `SURNAME`, `organizationIdentifier`, `T`, etc.) y decodifica su valor real en vez de volcar el DER; un OID que ni siquiera `BCStyle` reconoce sigue cayendo en `<oid>=<valor>` (hexadecimal solo como último recurso de la propia librería). **RED genuino**: un test con un sujeto con `emailAddress` construido con `X500NameBuilder`/`TestPki.issueSigningIdentityWithSubject` falló primero contra el código real (`#16...` presente) antes de cambiar el mapeador (`X509CertificateInfoMapperTest`, §7). El dominio (`CertificateInfo`) gana un campo `commonName` (nullable) con el `CN` del sujeto extraído por separado vía `X500Name.getRDNs(BCStyle.CN)`, expuesto también en `CertificateInfoDto` -- se decidió ponerlo en el **dominio**, no solo en el DTO de la API, porque `ArchitectureTest` prohíbe que `api` dependa de `infrastructure` (`apiDependsOnlyOnApplicationAndDomain`), así que la extracción vía Bouncy Castle solo puede vivir en `infrastructure.bouncycastle`, y el dominio es quien la expone hacia arriba. El orden de atributos cambia respecto al de la JDK (más específico primero, p.&nbsp;ej. `CN=...,O=...,C=ES`); se actualizaron en consecuencia los tests que comparaban contra el DN tal cual (`BcSignatureVerifierTest`).
- **Cadena de certificados desbordaba su tarjeta**: DNs largos sin espacios y huellas SHA-256 podían salirse del recuadro en "Detalles técnicos". Añadido `overflow-wrap: anywhere`/`word-break: break-word` a los bloques de DN/huella (incluidos los monoespaciados, `.mono`), `min-width: 0` en los contenedores grid/flex relevantes (`.chain-item`, `.signature-card`, `.detail-card`, `.signature-facts`, `.signature-name-wrap`) y `max-width: 100%` en las tarjetas. Cada certificado de la cadena ahora muestra el **CN en negrita** (`certificate.commonName`, con reserva al DN completo si faltara) y el **DN completo como texto secundario** debajo, en monoespaciado (`.chain-item-dn`), en vez de solo el DN crudo como antes.
- **Permisos y otros valores en crudo**: los permisos PDF (`PRINT`, `MODIFY`, ...) se mostraban tal cual venían de la API. Añadido un mapa `PERMISSION_TEXT` en `render.js` con las etiquetas en español pedidas (Imprimir, Anotar, Modificar, Rellenar formularios, Extraer para accesibilidad, Ensamblar, Imprimir en alta calidad, Extraer contenido); los códigos de la API (`SecurityInfoDto.permissions()`) no cambian. Se revisaron el resto de valores mostrados al usuario (rotación/orientación, estado PDF/A, revocación, integridad, cadena de confianza): ya estaban todos traducidos desde T11/T11c (`ORIENTATION_TEXT`, `PDFA_STATUS_TEXT`, `REVOCATION_STATE_TEXT`, `INTEGRITY_TEXT`, `CHAIN_STATUS_TEXT`), y las dos únicas secciones de análisis (`AnalysisSection.PDFA`/`SIGNATURES`) ya tenían traducción explícita en `sectionSpanish`.
- **Footer con referencia institucional**: el pie de página mencionaba "COAM" por nombre. Sustituido por un pie neutro (nombre del proyecto + enlace al repositorio de GitHub); no queda ninguna referencia a "COAM" en ningún fichero de `static/` (verificado con `grep -rniE coam`). No se ha tocado el paquete Java (`com.coam.pdfvalidator`) ni el `groupId` de Maven, fuera del alcance de este cambio.

**Verificación manual (Playwright MCP, puerto 8081 -- el 8963 por defecto estaba ocupado por otro proceso en la máquina de desarrollo)**: PDF de prueba generado con `TestPki.issueSigningIdentityWithSubject` (DN largo con `emailAddress`) firmado con `TestPdfSigner.sign`. El DN se muestra completo, legible y con `E=...@...` decodificado; el CN aparece en negrita como cabecera de la firma y de cada entrada de la cadena; los permisos aparecen en español; la tarjeta de la cadena de certificados no se desborda ni en escritorio (1280&nbsp;px) ni a 375&nbsp;px de ancho, en tema claro y oscuro (`document.documentElement.scrollWidth === clientWidth` en ambos casos); sin errores ni avisos en la consola del navegador. Aplicación detenida al terminar.

### 2.17 Incidencias PDF/A bilingües, "Cifrado y permisos" y nombre común sin escapes (T11g, T11h)

- **PDF/A en español (T11g)**: ver "Incidencias bilingües" en §2.8. El DTO `PdfaIssueDto` gana `messageEs` (anulable).
- **Tarjeta "Cifrado y permisos" (T11h)**: la etiqueta y el valor de cifrado van en una sola línea ("Cifrado: No") en lugar de apilados; los permisos llevan la etiqueta visible "Permisos del documento" y forman una lista (`<ul>` con `aria-labelledby` apuntando a esa etiqueta), con los mismos chips y el espaciado de `--space-*`, en ambos temas.
- **Nombre común (CN) sin escapes (T11h, backend, TDD)**: `X509CertificateInfoMapper` obtenía el CN con `IETFUtils.valueToString`, que conserva el escape RFC 2253 (`PEREZ\, JUAN \+ ...`). Ahora lee el valor directamente del atributo `CN` (`X500Name#getRDNs(BCStyle.CN)` + `ASN1String#getString()`), también cuando el CN comparte un RDN multivalor con otros atributos (antes se tomaba el primer atributo del RDN, que podía ser otro); un CN que no sea de tipo cadena ASN.1 o un sujeto sin CN dan `null`. Tests nuevos: coma/más/comillas, sin CN, RDN multivalor, valor no cadena y el respaldo cuando el DER del principal no se puede releer.
- **Tests de cadena PKIX**: el ayudante de `PkixCertificateChainValidatorTest` reutiliza ahora `X509CertificateInfoMapper.toDomain` en vez de construir DNs a mano, para que no pueda divergir del formato de producción.
- **Carrera "Validar este PDF" (T11h)**: `sign.js` usa un contador (`validationToken`) que se incrementa al iniciar una nueva firma, cancelar o elegir otro archivo; si la validación en curso termina después, ya no mueve el foco ni el desplazamiento de la página.

**Perfil de recursos (actualizado: 80 MB de subida, contenedor de 2 GB).** El límite de subida es de **80 MB** (`spring.servlet.multipart.max-file-size=80MB`, `max-request-size=81MB`; el cliente web valida lo mismo en `dom.js`). La imagen fija `JAVA_TOOL_OPTIONS="-XX:+UseSerialGC -Xms64m -Xmx1024m -XX:MaxMetaspaceSize=96m -XX:ReservedCodeCacheSize=48m -XX:MaxDirectMemorySize=32m -Xss512k -XX:+UseCompactObjectHeaders -XX:+ExitOnOutOfMemoryError"` y Compose limita el contenedor a **2 GB** (`mem_limit: 2g`) con un `tmpfs` de 256 MB para `/tmp`. El límite del contenedor cuenta *toda* la memoria del proceso (no solo el *heap*), así que cada región tiene un tope explícito y la suma en el peor caso queda por debajo del límite; si se superara, el kernel mataría el contenedor sin ningún error de Java.

| Región | Tope | Opción |
|---|---|---|
| *Heap* | 1024 MB | `-Xmx1024m` (`-Xms64m` inicial) |
| *Metaspace* | 96 MB | `-XX:MaxMetaspaceSize=96m` |
| Caché de código | 48 MB | `-XX:ReservedCodeCacheSize=48m` |
| *Buffers* directos | 32 MB | `-XX:MaxDirectMemorySize=32m` |
| Pilas de hilos | 20 MB | ~40 hilos (20 de Tomcat + JIT/VM/varios) × 512 KB (`-Xss512k`) |
| Nativa restante | 64 MB | *arenas* de `malloc`, estructuras del GC, CDS, libc (estimación) |
| **Subtotal JVM** | **1284 MB** | |
| `/tmp` (`tmpfs`) | 256 MB | `tmpfs: /tmp:size=256m` (cuenta contra el límite cuando se llena; con `max-concurrent=2` caben 2 subidas de 81 MB = 162 MB y quedan ~90 MB libres; con 160 MB no había margen) |
| **Total en el peor caso** | **1540 MB** | ~500 MB de margen bajo 2048 MB |

**Medición real (2026-09-29, VPS de OVHcloud de 4 GB, Ubuntu 24.04, PDF sintético de 83 MB generado con `LargePdfGenerator`, peticiones desde el propio servidor):** con `max-concurrent=1`, una subida → 200 en 4,7 s; 5 subidas simultáneas y `acquire-timeout=5s` → 2 × 200 y 3 × 503 `busy`, `memory.peak` del *cgroup* **753 MiB**. Con `max-concurrent=2` y `acquire-timeout=30s`, 5 subidas simultáneas → **5 × 200** (4 a 14 s), `memory.peak` **1013 MiB de 2048**, sin reinicios, sin OOM-kill y sin `OutOfMemoryError`. Por eso los valores por defecto pasan a `max-concurrent=2` y `acquire-timeout=30s` (un análisis de 80 MB tarda 4-7 s, y con 5 s de espera la mayoría de las peticiones simultáneas recibían un 503, que el navegador puede mostrar como «no se puede contactar con el servidor» porque el servidor cierra la conexión sin leer el cuerpo). Para una VM pequeña, sobrescribe `JAVA_TOOL_OPTIONS`, `mem_limit` y el `tmpfs` a la vez y baja el límite de subida. Las secciones siguientes describen el diseño del *bulkhead* y las mediciones históricas con el perfil anterior de 512 MB y PDF de ~19 MB.

Otras opciones: `-XX:+UseSerialGC` (sin hilos de GC paralelos: menor consumo en una VM de 1 vCPU/1 GB), `-XX:+UseCompactObjectHeaders` (cabeceras de objeto compactas, estable en Java 25) y `-XX:+ExitOnOutOfMemoryError` (ante un `OutOfMemoryError` la JVM termina y `restart: unless-stopped` la levanta, en vez de quedar en un estado degradado). La concurrencia de peticiones está acotada en `application.yml` (`server.tomcat.threads.max: 20`, `server.tomcat.accept-count: 20`; se pueden sobrescribir con `SERVER_TOMCAT_THREADS_MAX` y `SERVER_TOMCAT_ACCEPT_COUNT`) para que el término de hilos y el uso de `/tmp` se mantengan dentro del presupuesto. Todas las opciones se han comprobado con JDK 25 (la JVM las acepta y la aplicación arranca con `/actuator/health` → `UP`).

**Límite de análisis simultáneos (*bulkhead*, T12c).** Un PDF de 20 MB se lee entero, y PDFBox y *preflight* multiplican esa memoria (estimación de trabajo: ~100 MB de *heap* en el peor caso por análisis: 20 MB subidos + 20 MB de *bytes* + estructuras de PDFBox/*preflight*). Los 20 hilos de Tomcat, por sí solos, admitirían 20 análisis a la vez (~2 GB), muy por encima de los 240 MB de *heap*. Por eso solo se permiten `pdfvalidator.analysis.max-concurrent` análisis simultáneos (por defecto **1**, ~100 MB de los 240 MB de *heap*; con 2 serían ~200 MB, sin margen en una VM de 512 MB), implementado como un filtro de servlet (`AnalysisBulkheadFilter`, capa `api`) que toma un permiso de un `Semaphore` (`AnalysisBulkhead`) **antes** de que Spring lea la subida multiparte y lo libera siempre en un `finally` (éxito, excepción o cliente que se desconecta). Una petición espera hasta `pdfvalidator.analysis.acquire-timeout` (por defecto **5 s**) un permiso; si no lo consigue, responde **503** con `ProblemDetail` `urn:pdfvalidator:error:busy` y la cabecera `Retry-After` (el *timeout* en segundos, mínimo 1). La interfaz web lo muestra como "El servicio está ocupado analizando otros documentos. Inténtalo de nuevo en unos segundos.".

*Por qué un filtro y no el controlador:* Spring resuelve el multiparte *antes* de invocar al controlador, así que un permiso tomado allí dejaría hasta 20 subidas de 20 MB ya almacenadas. Con el filtro, tanto el almacenamiento de la subida como el análisis quedan acotados a `max-concurrent`.

*Alcance del filtro (T12d):* se aplica a **toda petición `multipart/*`, en cualquier ruta**, no a la URL exacta del *endpoint*. Comparar la ruta era una vía de evasión: el contenedor y Spring MVC aceptan varias grafías de la misma ruta (parámetros de ruta `;jsessionid=x`, codificación porcentual `/%61nalyze`, segmentos duplicados o de punto, barra final, mayúsculas), y cualquiera que el filtro no reconociera se almacenaba y analizaba sin permiso. Decidir por el tipo de contenido falla en el lado seguro: el único *endpoint* multiparte es la subida de análisis, así que no afecta a nada más, y cualquier otra ruta con un cuerpo multiparte también se cuenta. La ruta del *endpoint* se escribe en un solo sitio (`PdfAnalysisController.ANALYZE_PATH`). Comprobado contra el servidor real (`AnalysisBulkheadIntegrationTest`), con el único permiso ocupado, para cada variante:

| Variante de la URL | Sin contención | Con el permiso ocupado |
|---|---|---|
| `/api/v1/pdf/analyze` | 200 (controlador) | **503** (*bulkhead*) |
| `/api/v1/pdf/analyze;jsessionid=x` | 200 (llegaba al controlador sin límite antes de T12d) | **503** |
| `/api/v1/pdf/%61nalyze` | 200 (ídem) | **503** |
| `/api/v1/pdf/analyze/` | 404 (Spring no enruta la barra final) | **503** |
| `//api/v1/pdf/analyze` | 404 | **503** |
| `/API/v1/pdf/analyze` | 404 | **503** |
| `/api/v1/pdf/./analyze`, `/api/v1/pdf/x/../analyze` | 404 | **503** |

*Rechazo sin leer el cuerpo:* la petición rechazada no llega a leer la subida, así que el `503` lleva `Connection: close` y el contenedor cierra la conexión en vez de intentar vaciar hasta 20 MB (Tomcat solo vacía hasta `maxSwallowSize`, 2 MB por defecto, antes de cerrar; se mantiene el valor por defecto). Pruebas con un *socket* crudo: con un cuerpo pequeño y con uno de 20 MB anunciado y enviado en paralelo, el cliente recibe el `503` con `Connection: close` de inmediato (Tomcat ya cierra la conexión en un 503; la cabecera explícita hace que no dependa del contenedor).

*Búfer de subida:* `spring.servlet.multipart.file-size-threshold=0B` y `location=${java.io.tmpdir}`: cada subida se escribe directamente a `/tmp` (tmpfs), no al *heap*. Con 2 análisis simultáneos, `/tmp` contiene como máximo 2 × 20 MB = **40 MB** de los 64 MB del `tmpfs` (24 MB de margen para Tomcat/JVM), y el *heap* se reserva para PDFBox. Guardar la subida en memoria sumaría otros 20 MB de *heap* por análisis (el recurso escaso) sin ahorrar RAM real, porque el `tmpfs` también se carga contra el límite del contenedor; un `tmpfs` lleno da un `IOException` (500 controlado), un *heap* lleno mata el proceso. La tabla de presupuesto no cambia (el `tmpfs` ya se cuenta lleno: 492 MB en el peor caso).

*Interacción con Tomcat:* `server.tomcat.threads.max=20` y `accept-count=20` solo **encolan** conexiones (20 hilos activos + 20 en cola de aceptación; más allá, la conexión se rechaza). Un hilo que espera permiso permanece bloqueado como máximo `acquire-timeout`, antes de leer el cuerpo de la subida, así que las peticiones en espera no consumen *heap* ni `/tmp`. El *bulkhead* es lo que realmente acota la memoria.

*Ajuste:* `PDFVALIDATOR_ANALYSIS_MAX_CONCURRENT` y `PDFVALIDATOR_ANALYSIS_ACQUIRE_TIMEOUT` (ver `docker-compose.yml`). Subir `max-concurrent` sube el peor caso (≈ 100 MB de *heap* y 20 MB de `/tmp` por análisis): reajusta `-Xmx` y el `tmpfs` (y el límite del contenedor) en consecuencia.

**Prueba de carga en CI (T12c).** El job `docker`, tras la prueba de humo, genera un PDF válido de ~19 MB (194 páginas; `.github/scripts/LargePdfGenerator.java`, sin dependencias, ejecutado con el JDK del *runner* mediante `java LargePdfGenerator.java`; elegido por ser robusto y no requerir Python ni el *classpath* anidado de Spring Boot), arranca un contenedor con los mismos límites (512 MB, `read_only`, `tmpfs` de 64 MB) y le envía **5 subidas concurrentes** con `curl --max-time 120`. Falla si alguna respuesta no es 200 o 503 (un 503 debe llevar el `type` `busy`), si ninguna es 200, si el contenedor se reinicia (`RestartCount` ≠ 0), lo mata el OOM (`OOMKilled`) o aparece `OutOfMemoryError` en los logs. Imprime las muestras de `docker stats` (una por segundo), el pico de memoria muestreado y `memory.peak` del *cgroup*. En local (sin Docker), con el jar, `-Xmx240m` y `max-concurrent=1`, 4 subidas simultáneas de un PDF de 19,9 MB dieron 1 × 200 y 3 × 503 con `Retry-After: 1`; con los valores por defecto las 3 subidas se atendieron en serie (200) en ~1,4 s.

*Medición real en CI (2026-09-29, *runner* `ubuntu` de GitHub, PDF sintético de 19,9 MB, 5 subidas concurrentes, `max-concurrent=2`, contenedor de 512 MB):* las 5 peticiones respondieron 200 (atendidas de 2 en 2, el *bulkhead* funciona), `running=true`, `RestartCount=0`, `OOMKilled=false`; pico muestreado con `docker stats` **439,9 MiB** y `memory.peak` del *cgroup* **502,3 MiB de 512** (incluye las dos subidas de ~20 MB en el `tmpfs`). **El margen real es de solo ~10 MB con `max-concurrent=2` y subidas de 20 MB.** **Decisión (2026-09-29): el valor por defecto es `max-concurrent=1`** para la VM de 512 MB (peor caso ≈ 100 MB de *heap* y 20 MB de `/tmp`, margen amplio). Con 2 el margen medido era de ~10 MB, demasiado justo. Con `acquire-timeout=5s` y ~1-2 s por análisis de 19 MB, la mayoría de las peticiones simultáneas siguen recibiendo 200 y el resto un 503 `busy` con `Retry-After`. Para una VM de 1 GB o más se puede subir con `PDFVALIDATOR_ANALYSIS_MAX_CONCURRENT=2` (y reajustar el límite del contenedor, `-Xmx` y `tmpfs`). El paso de CI **no** falla por el porcentaje de `memory.peak` (incluye caché de páginas recuperable y `tmpfs`, así que es una señal ruidosa que ya rozaba el 98 %): lo imprime solo como información y falla ante señales reales de OOM: contador `oom_kill` > 0 en `/sys/fs/cgroup/memory.events`, `OOMKilled=true`, `RestartCount` > 0, contenedor parado o `java.lang.OutOfMemoryError` en los logs (ignorando el *banner* de la JVM con `-XX:+ExitOnOutOfMemoryError`). El `WARN` de PDFBox "Using fallback font" (fuente estándar no incrustada, habitual en PDF reales) inundaba el log; `application.yml` deja el *logger* `org.apache.pdfbox.pdmodel.font` en `ERROR`.

**Endurecimiento.** Usuario no root (`app`, uid 10001); `read_only: true` con `/tmp` como `tmpfs` de 64 MB (única ruta escribible: directorio de trabajo de Tomcat, subidas multiparte y ficheros temporales de PDFBox); `security_opt: no-new-privileges:true`; `cap_drop: [ALL]`; `HEALTHCHECK` con `wget` sobre `/actuator/health` (Docker solo marca el contenedor como `unhealthy`: `restart: unless-stopped` reinicia los que terminan, no los no saludables; para eso haría falta un vigilante externo como `autoheal`); Actuator solo expone `health` e `info`.

**Configuración por variables de entorno** (bloque `environment` de `docker-compose.yml`, comentado por defecto): `PDFVALIDATOR_TRUSTSTORE_EXTERNAL_DIR`, `PDFVALIDATOR_REVOCATION_TIMEOUT`, `PDFVALIDATOR_ANALYSIS_MAX_CONCURRENT`, `PDFVALIDATOR_ANALYSIS_ACQUIRE_TIMEOUT`, `SERVER_PORT`. Para añadir raíces de confianza propias, monta un directorio de solo lectura con un certificado por fichero (`volumes: ["./mi-truststore:/truststore:ro"]`) y apunta `PDFVALIDATOR_TRUSTSTORE_EXTERNAL_DIR=/truststore`; se suman a las raíces españolas empaquetadas (§2.7).

**Estado de la verificación (2026-09-29).** El job `docker` de CI construye la imagen, la arranca con `--memory=2g --read-only --tmpfs /tmp:size=256m`, espera a `/actuator/health` = `UP` (hasta ~90 s), comprueba `GET /` = 200 e imprime `docker stats`, y después ejecuta la prueba de carga descrita arriba (5 subidas simultáneas de ~79 MB); no se publica ninguna imagen. La imagen también se ha construido y probado en un VPS real (ver «Despliegue en un VPS» más abajo). No se ha probado en el equipo de desarrollo porque allí el daemon de Docker no estaba en marcha.

`chainStatus` depende de si el certificado firmante llega a una de las raíces configuradas (§2.7); `sectionErrors` solo contiene entradas si una sección falló de forma inesperada (§2.9/§2.11); `verdict`/`verdictReasons` y `overallVerdict`/`modifiedAfterLastSignature` son el veredicto general por firma y a nivel de documento (§2.13).

Con `checkRevocation=true` (§2.12) y una cadena `TRUSTED`, `revocation` se rellena de verdad:

```bash
curl -F "file=@/ruta/a/documento-firmado.pdf" "http://localhost:8963/api/v1/pdf/analyze?checkRevocation=true"
```

```json
"revocation": { "state": "GOOD", "source": "http://ocsp.ejemplo.org/ee", "detail": null }
```

Si la cadena **no** es `TRUSTED` (como en el ejemplo de arriba, `UNTRUSTED_ROOT`), `revocation` se queda en `NOT_CHECKED` con un motivo explícito aunque `checkRevocation=true` — la comprobación de revocación nunca se intenta para una cadena que no es de confianza (§2.12):

```json
"revocation": { "state": "NOT_CHECKED", "source": null, "detail": "revocation not checked: certificate chain is not trusted" }
```

## 7. Tests y calidad

El proyecto se desarrolla con **TDD** (primero el test en rojo, luego la implementación en verde y después la refactorización).

Los PDFs de prueba **se generan por código** (`fixtures/TestPdfFactory`): una CA de pruebas en memoria firma documentos, y a partir de ellos se crean variantes manipuladas, con actualización incremental, rotadas, cifradas o corruptas. Así los tests son reproducibles y no dependen de ficheros con datos personales. Se añadirán 2-3 PDFs reales firmados para los tests de integración (⏳).

## 10. Decisiones técnicas

- **Perfil de recursos de 2 GB y subidas de 80 MB en lugar de la VM de 512 MB – 1 GB del enunciado.** El proyecto se diseñó y se midió primero para 512 MB con PDF de hasta 20 MB y un análisis a la vez (5 × 200 en CI, sin OOM; ver §4). Tras desplegarlo, se decidió admitir PDF reales de hasta 80 MB (planos y documentación de visado), que no caben con margen en 512 MB: PDFBox y *preflight* multiplican la memoria del documento. Con 2 GB, 2 análisis simultáneos y 30 s de espera, 5 subidas de 83 MB a la vez dieron 5 × 200 y un pico de 1013 MiB. El perfil de 512 MB sigue siendo posible sobrescribiendo `JAVA_TOOL_OPTIONS`, `mem_limit`, el `tmpfs` y el límite de subida (valores documentados en §4).
- **Spring Boot 4.1.1 en lugar de 3.x.** El documento del TFM recomendaba Spring Boot 3.x, pero el soporte OSS de la rama 3.5 (la última 3.x) terminó el 30/06/2026. La 4.1 tiene soporte hasta el 31/07/2027. En Boot 4 el starter web pasa a llamarse `spring-boot-starter-webmvc`.
- **Java 25 en lugar de 21.** Java 25 es la LTS más reciente (soporte hasta 2031) y está dentro del rango soportado por Spring Boot 4.1 (17–26). Aporta mejoras útiles en una VM de poca memoria, como las *compact object headers*. Se descartó Java 27 porque no es LTS y queda fuera del rango soportado por Spring Boot 4.1.
- **OpenLogic en local, Temurin en CI y contenedor.** Las dos distribuciones son OpenJDK con la misma licencia (GPLv2 + Classpath Exception) y la misma política criptográfica (`crypto.policy=unlimited`); no hay diferencias funcionales para el proyecto.
- **PDF/A-1b únicamente.** El módulo *preflight* de PDFBox solo valida PDF/A-1b. Para PDF/A-2/3 se informará de la declaración XMP, pero no se validará formalmente.
- **Revocación opcional y acotada.** Las consultas OCSP/CRL dependen de la red, así que se activan con un parámetro, tienen un timeout de 2 s y, si fallan, el resultado es `UNKNOWN` sin bloquear el resto del análisis. Implementación real desde T10 (§2.12); antes de T10 era un `NoOpRevocationChecker` provisional.
- **Sin lista de confianza europea (TSL).** La cadena se valida contra un almacén de raíces configurable con las CA españolas.
- **Documento cifrado (contraseña no vacía) o corrupto: se propaga, no se degrada a un informe parcial (T08).** `AnalyzePdfUseCase` deja que `EncryptedPdfException`/`InvalidPdfException` salgan de `analyze(...)` sin capturarlas: no hay un informe parcial razonable para un documento que ni siquiera se pudo abrir. La capa REST (T09) mapea ambas a `422` (§2.11/§4).
- **`NoOpRevocationChecker` como implementación provisional (T08, superada por T10).** Mientras el `RevocationChecker` real (OCSP/CRL) no existía, se informaba `NOT_CHECKED` con un detalle explícito ("revocation checking not available yet") en vez de fingir que se comprobó. Desde T10 el cableado real usa `CompositeRevocationChecker`; la clase se conserva solo porque un test de integración (`AnalyzePdfUseCaseIntegrationTest`) todavía la usa como *stub* de un puerto que no es el foco de ese test.
- **(T08b) Un resultado vacío nunca debe ser indistinguible de un fallo silencioso.** `PdfAnalysisReport` gana `sectionErrors()`: cuando `SignatureVerifier`/`PdfaConformanceValidator` fallan de forma inesperada, se añade una entrada explícita en vez de dejar que una lista de firmas vacía se confunda con "documento sin firmar".
- **(T09) El cableado del caso de uso vive fuera de las cuatro capas, en el paquete raíz.** `ArchitectureTest` prohíbe que `infrastructure` dependa de `application`; como el `@Bean` de `AnalyzePdfUseCase` necesariamente depende de ambos, se cablea en `com.coam.pdfvalidator.UseCaseConfiguration` (junto a `PdfValidatorApplication`), la "raíz de composición" convencional de una arquitectura hexagonal, en vez de forzar esa dependencia dentro de `infrastructure.config`.
- **(T09) DTOs explícitos, nunca el dominio serializado directamente; nunca la codificación DER de un certificado.** `PdfAnalysisReportMapper` traduce cada tipo de dominio a un DTO propio; los certificados se identifican por una huella SHA-256, no por sus bytes DER.
- **(T09) `@RestControllerAdvice` acotado a `PdfAnalysisController`.** Sin `assignableTypes`, un `@ExceptionHandler(Exception.class)` genérico se aplica a toda la aplicación (incluidos Actuator, *springdoc* y cualquier recurso estático), pudiendo convertir un `404` legítimo de Spring en un `500` propio — detectado ejecutando la aplicación en local, no solo con tests de *slice* (§2.11).
- **(T09c) Integridad criptográfica y validez del certificado son dos hechos separados.** La firma se verifica siempre con la clave pública del firmante (nunca con el certificado completo), para que Bouncy Castle no acople por su cuenta la verificación de la firma a la vigencia del certificado en el instante de firma; esa vigencia se comprueba por separado y se informa como una nota de anomalía, nunca como `INVALID_SIGNATURE` (§2.2).
- **(T09c) Normalización de `digestAlgorithm` deliberadamente acotada a OIDs inequívocos.** Solo se normalizan OIDs de algoritmo de firma que nombran exactamente un algoritmo de resumen (RSA PKCS#1 v1.5, ECDSA, DSA clásico); `id-RSASSA-PSS` y `rsaEncryption` a secas se dejan sin normalizar porque no nombran un resumen sin ambigüedad (§2.2).
- **(T09c) `digestAlgorithm` mal etiquetado se verifica sin pasar por `SignerInformation#verify(...)`.** Disassemblar `SignerInformation.class` (bcpkix-jdk18on 1.86) mostró que, para un CMS sin atributos firmados y firma RSA, Bouncy Castle reconstruye internamente el `DigestInfo` PKCS#1 a partir del propio `digestAlgorithm` sin normalizarlo (su `translateBrokenRSAPkcs7` solo corrige la variante histórica con SHA-1, no SHA-224/256/384/512): el resumen calculado es correcto, pero la verificación final seguía fallando en un fichero real. Se construye el `ContentVerifier` directamente con el OID mal etiquetado (que, tomado tal cual, ya es un algoritmo de firma completo y válido), evitando esa reconstrucción interna (§2.2).
- **(T09c) La cadena de certificados se extrae siempre que el CMS se pudo parsear, incluso si la verificación falla.** Antes, cualquier fallo de verificación (incluida la comprobación de vigencia del certificado que ya no se hace) descartaba también la cadena ya extraída; ahora solo un fallo de *parseo* del propio CMS deja la cadena vacía (§2.2).
- **(T09b) El límite de subida necesita un *advice* propio, sin acotar.** `MaxUploadSizeExceededException` se lanza antes de que Spring resuelva ningún *handler* (`DispatcherServlet#doDispatch` resuelve el multipart antes de la búsqueda de *handler*), así que un *advice* acotado a `PdfAnalysisController` nunca la ve; se maneja en un segundo *advice* sin acotar que solo reacciona a esa excepción, sin repetir el problema del `404` de Actuator (§2.11).
- **(T09b) Ningún mensaje de excepción llega al cliente sin pasar por un texto fijo.** `SectionError`, la nota de anomalía de enriquecimiento de firma y el mensaje de `UploadReadException` usan siempre un texto estable y no sensible; el detalle real se registra por log, nunca en la respuesta JSON (§2.9/§2.11).
- **(T09c) Anclas de confianza no autofirmadas: el modelo eIDAS lo exige.** Una Lista de Confianza de la UE puede publicar una CA emisora cualificada sin publicar su propia raíz (caso Camerfirma); `PkixCertificateChainValidator` no asume que un ancla deba ser autofirmada — la JDK ya lo soporta de forma nativa —, verificado con un test dedicado (§2.7).
- **(T09d) Una CA emisora también puede ser ancla aunque su propia raíz ya esté empaquetada.** El caso Camerfirma (T09c) es "la raíz ni siquiera está publicada"; el caso FNMT (T09d) es distinto y más común: la raíz sí está, pero el CMS de un PDF real no incluye la intermedia, así que sin esa intermedia como ancla la ruta PKIX se queda corta (`INCOMPLETE_CHAIN`) aunque la raíz sea de confianza. Ambos casos comparten la misma solución (§2.7).
- **(T09d) Solo se empaquetan certificados extraídos de la propia TSL, nunca de un PDF de usuario.** Igual que con Camerfirma, las dos CA emisoras de FNMT se obtuvieron descargando `https://tsl.digital.gob.es/TSL.xml` (localizada a través de la LOTL de la UE) y extrayendo el certificado embebido en el `TSPService` correspondiente — nunca copiando un certificado visto en uno de los dos PDFs reales usados para la verificación manual.
- **(T10) La revocación solo se comprueba para una cadena `TRUSTED`, nunca antes.** Las URLs OCSP/CRL viven dentro de extensiones de un certificado potencialmente hostil (el uploader controla el CMS); comprobarlas incondicionalmente sería un vector directo de SSRF a través de un certificado autofirmado y fabricado a mano. Para una cadena `TRUSTED` esos certificados los escribió una CA real, cerrando ese vector en el origen — la guarda de red (siguiente decisión) queda como defensa en profundidad, no como la única barrera (§2.12).
- **(T10) El certificado y el emisor para revocación vienen de `CertificateChainValidator#validatedPath`, no de la cadena presentada.** `SignatureVerifier` extrae la cadena directamente del CMS (controlado por el uploader), que podría incluir un certificado adicional irrelevante para la ruta de confianza real construida por PKIX. `validatedPath` (nuevo método por defecto del puerto, implementado de verdad solo en `PkixCertificateChainValidator`) devuelve exactamente los certificados que PKIX usó para llegar a `TRUSTED`, incluido el del ancla cuando esta no viene en el CMS (§2.7/§2.12).
- **(T10) `PinnedHttpClient`: un cliente HTTP/1.1 propio sobre `Socket`, no `java.net.http.HttpClient`, para evitar el *DNS rebinding*.** `java.net.http.HttpClient` resuelve el nombre de host por su cuenta al conectar, después de que la guarda ya lo hubiera resuelto y validado — dos resoluciones independientes que un DNS autoritativo hostil puede responder de forma distinta, sorteando la guarda. La solución resuelve una sola vez y ancla la conexión a esa dirección exacta (§2.12).
- **(T10) Solo `http`, nunca `https`, para OCSP/CRL.** Anclar una conexión TLS a una IP concreta mientras se preserva la verificación SNI/nombre de host del nombre original es posible pero se consideró desproporcionado para una función opcional y de mejor esfuerzo; se rechaza explícitamente en vez de una implementación TLS parcial. Ninguna de las dos entidades reales probadas (FNMT, Camerfirma) lo necesita: ambas publican OCSP/CRL por `http://` (§2.12).
- **(T10) Servidor HTTP de test propio (`com.sun.net.httpserver.HttpServer`) en vez de WireMock.** Elimina cualquier riesgo de conflicto de classpath entre el Jetty embebido de WireMock y el propio Jetty de Spring Boot 4.1.1, sin depender de una nueva librería de test ni tener que verificar antes esa compatibilidad (§2.12).
- **(T10b) Un caso límite de revocación "no comprobada" necesitaba un motivo explícito.** Una cadena ya `TRUSTED` cuya `validatedPath` volviera vacía (algo que no debería pasar en la práctica, pero que el código no descartaba) devolvía el mismo marcador `RevocationStatus.notChecked()` que "el usuario no pidió comprobar revocación" -- dos situaciones muy distintas que se veían igual en la respuesta. Ahora lleva siempre un detalle explícito (`"validated certification path unavailable"`).
- **(T10b) Los envoltorios de seguridad de `CompositeRevocationChecker` registran solo el nombre de la clase de la excepción, nunca su mensaje.** Igual que en el resto del proyecto (§10, T09b): un detalle de excepción inesperado puede llevar información de red o de protocolo que no debe acabar en el log tal cual; el nombre de la clase basta para diagnosticar sin arriesgar nada sensible.
- **(T11) Veredicto por firma como una política de dominio pura y separada, no lógica dispersa en el caso de uso.** `SignatureVerdictPolicy` vive en `domain/policy` (no en `application`) precisamente porque es una regla de negocio -- qué combinación de integridad/cadena/revocación cuenta como "válida" -- no un detalle de orquestación; se puede testear exhaustivamente sin ningún *fake* de puerto.
- **(T11) `SignatureReport`/`PdfAnalysisReport` ganan el veredicto sin romper ningún constructor existente.** `SignatureReport` añade un constructor de conveniencia con la forma original (10 argumentos), que reduce a la forma canónica (12 argumentos) con un veredicto de marcador seguro (`NOT_ADMITTED`, sin motivos) -- todos los *fixtures*/tests anteriores a T11 siguen compilando sin tocarlos. `PdfAnalysisReport.overallVerdict()`/`modifiedAfterLastSignature()` son métodos calculados a partir de `signatures()`, no componentes nuevos del *record*: no hay manera de que queden desincronizados con las firmas que realmente contiene, y tampoco obligan a tocar ningún `new PdfAnalysisReport(...)` existente.
- **(T11) `UNSUPPORTED` es `NOT_ADMITTED`, no `INVALID`; `REVOKED` es siempre `INVALID`.** Ambas, decisiones explícitas del usuario/proyecto, documentadas con su razonamiento completo en §2.13 (incluida la salvedad de que la revocación consultada es la actual, no la del instante de firma).
- **(T11) La regla de "cubierta por una firma posterior" es estructural, no una comparación de contenido.** Comprobar si alguna firma del documento es `INTACT` y cubre el fichero completo es barato y ya estaba disponible; diferenciar el contenido añadido entre dos revisiones incrementales sería una funcionalidad mucho más grande, fuera del alcance de esta tarea -- documentado como limitación explícita, no silenciada (§2.13).
- **(T11) Cabecera CSP mediante un filtro Spring acotado por ruta exacta, no un `url-pattern` de Servlet ni una etiqueta `<meta>`.** Un `url-pattern` de Servlet `"/"` es, por especificación, el mapeo por defecto -- coincide con *toda* petición, no solo la raíz literal. El filtro se registra ampliamente (`/*`) pero decide él mismo, comparando la ruta (relativa al *context path* desde T11c) contra una lista fija (`/`, `/index.html`, `/app.js`, `/styles.css`), así que Swagger UI/Actuator/la API nunca la reciben. Se prefirió una cabecera HTTP real (comprobable con `MockMvc`) frente a una etiqueta `<meta http-equiv="Content-Security-Policy">`, que además no soporta `frame-ancestors`.
- **(T11) Bug real de CSS encontrado en la verificación manual: `[hidden]` no ganaba siempre.** Documentado en detalle en §2.13; la lección general (no solo de este proyecto) es que una regla de igual especificidad que la del navegador para `[hidden]`, si va después en la cascada, gana -- conviene una única regla `!important` temprana en vez de acordarse de añadir `[hidden]` a cada selector nuevo.
- **(T11c) SECURITY: "cubierta por una firma posterior" exigía solo `INTACT`, no confianza -- permitía re-firmar un documento modificado con un certificado propio y que la firma original siguiera pareciendo válida.** Encontrado en la revisión de T11 (RDD). La corrección exige que **todas** las firmas posteriores estén ellas mismas admitidas (`VALID`), no solo que alguna sea `INTACT`; ver la explicación completa del ataque y la corrección en §2.13.
- **(T11c) `ANALYSIS_INCOMPLETE` en vez de dejar que una lista de firmas vacía por fallo se confunda con "sin firmar".** Mismo principio que `SectionError` (T08b, §10 arriba) aplicado al veredicto general: `PdfAnalysisReport.overallVerdict()` comprueba primero si `sectionErrors` contiene una entrada `SIGNATURES` antes de delegar en `SignatureVerdictPolicy`, en vez de dejar que `signatures().isEmpty()` decida por sí solo.
- **(T11c) La cabecera CSP debía compararse relativa al *context path*, no contra `getRequestURI()` tal cual.** `getRequestURI()` ya incluye el *context path* de despliegue; comparar sin restarlo es correcto solo mientras la aplicación se sirva desde la raíz (`""`), que es como se ejecuta hoy (§4) pero no una garantía para cualquier despliegue futuro -- corregido y probado con un *context path* real distinto de la raíz.
- **(T11b) `setForceWSMode(true)` NO se activa, a pesar de lo que su nombre sugiere.** Verificado leyendo directamente el código fuente de AutoScript 1.10.1 (`cargarAppAfirma`): ese flag fuerza el transporte de **servidor intermedio** (necesita *servlets* propios de guardado/recuperación -- justo lo que esta tarea pide evitar), no el modo WebSocket. Dejarlo desactivado hace que cualquier navegador de escritorio con soporte WebSocket use `AppAfirmaWebSocketClient` automáticamente, hablando directamente con AutoFirma sin ningún servidor en medio.
- **(T11b) AutoScript se vendorea sin modificar, como componente de terceros independiente**, en vez de mezclarlo con el código propio o reescribir su lógica -- ver el razonamiento completo de licencias en §13.
- **(T11b) El diálogo propio de AutoScript se desactiva (`SupportDialog.enableSupportDialog(false)`) en vez de relajar la CSP.** Ese diálogo inyecta un `<style>` con contenido en línea; en vez de añadir `'unsafe-inline'` a `style-src` únicamente para dar cabida a un componente de terceros que además duplicaría la propia interfaz de espera/cancelar de esta pantalla, se desactiva por completo.
- **(T11b) `connect-src`/`frame-src` ampliados con lo estrictamente necesario, nunca `'unsafe-eval'`/`'unsafe-inline'` para scripts.** Verificado en el código de AutoScript: no usa `eval()`/`Function()` ni genera `<script>` en línea. Solo hizo falta permitir `wss://127.0.0.1:*`/`https://127.0.0.1:*` (el cliente WebSocket y su alternativa de compatibilidad, ambos a un puerto local dinámico) y `frame-src 'self' afirma:` (el `<iframe>` oculto que Firefox/Safari usan para lanzar AutoFirma; Chrome/Edge navegan directamente y no lo necesitan).
- **(T11b) Página única con pestañas, no un `firmar.html` separado.** Permite reutilizar sin duplicar la cabecera, el tema, el filtro CSP y, sobre todo, `render.js` para el botón "Validar este PDF" -- ver §2.14.
- **(T11d) Javadoc de `SignatureVerdictPolicy.laterSignatureCoverage` alineado con la implementación real.** El texto anterior describía la comprobación como "¿el `ByteRangeCoverage` de cada firma posterior llega al final real del fichero y es en sí misma `INTACT`?", pero el código nunca inspecciona `ByteRangeCoverage` en este método: solo exige que el **veredicto ya calculado** de cada firma posterior sea `VALID` -- lo que además permite, correctamente, que una firma posterior en sí misma `MODIFIED_AFTER_SIGNING` cuente igualmente si una firma aún más posterior la cubre y es admitida (cobertura transitiva). Corregido para describir el mecanismo real (§2.13).
- **(T11d) Los avisos de la revisión de T11c sobre CSP/*charset* eran, en su mayoría, ya comportamiento correcto sin cobertura de test.** `PROTECTED_PATHS.contains(...)` ya comparaba por igualdad exacta de cadena (nunca por subcadena) y el filtro ya forzaba `UTF-8` correctamente en sus cuatro rutas -- verificado leyendo el código antes de escribir ningún test nuevo. Se añadieron tests de regresión (`StaticContentSecurityTest`/`CspHeaderFilterTest`, §7) para dejar esas garantías explícitas y detectar cualquier regresión futura, sin necesidad de tocar `CspHeaderFilter`.
- **(T11e) Excepción de diseño acotada, nunca silenciar el detector globalmente.** El aviso `monotonous-spacing` de Impeccable seguía disparándose tras establecer una cadencia de espaciado real, porque cuenta la frecuencia bruta del valor más pequeño en toda la hoja de estilos (dominado por agrupaciones apretadas legítimas). Se descartó `ignore-rule` (silenciaría el aviso en todo el proyecto, incluidos futuros regresiones reales) a favor de `ignore-value ... --file index.html`, acotado a este fichero y con el motivo documentado en `.impeccable/config.json`.
- **(T11e) `switchTab` compartida en `dom.js`, no duplicada entre `app.js` y `sign.js`.** El botón "Validar este PDF" necesitaba cambiar a la pestaña "Validar" antes de mostrar el resultado. Mover la función a `dom.js` (en vez de importarla de `app.js` a `sign.js`, o de `sign.js` a `app.js`) evita un ciclo de importación entre ES *modules*: `dom.js` es deliberadamente el módulo hoja del que dependen tanto `app.js` como `sign.js`, nunca al revés.
- **(⏳ mejora futura, T14) Carga automática de anclas desde la Lista de Confianza española.** En vez de curar manualmente cada ancla (como se hace hoy), una tarea futura opcional podría descargar y verificar `https://tsl.digital.gob.es/TSL.xml` (resuelta a través de la LOTL de la UE), interpretar los `TSPService` de tipo CA/QC con su estado (`granted`/`withdrawn` con semántica de vigencia por fecha), verificar la firma XML de la propia TSL contra los certificados firmantes publicados por la LOTL, y cachear el resultado con una vuelta al almacén empaquetado si la red no está disponible — cubriendo así todas las CA cualificadas españolas sin mantenerlas a mano. No implementado; ver la tarea T14 en `odd/tasks/pdf-validator.md`.
