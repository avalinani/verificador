# Feature: pdf-validator

## Objective
Stateless web service (TFM) that audits a PDF in one pass: signature integrity (PAdES/CMS), post-signature modifications, RFC 3161 timestamps, X.509 chain trust, optional OCSP/CRL revocation, PDF/A-1b conformance, page properties.

### T03b — Reader robustness

- **Revision counting** (`infrastructure/pdfbox/RevisionCounter`, new class): walks the xref/trailer chain backwards from the last `startxref`, following each section's `/Prev` link (bounded to stop at the next `stream`/`startxref` keyword so an unrelated `/Prev`-looking byte sequence elsewhere in the file cannot be picked up), counting one hop per xref section. Detects a linearized layout by searching for a `/Linearized` marker in the first 2048 bytes and, when present, does not count the hint-section xref as a separate revision. Falls back to the previous `%%EOF`-marker heuristic only if no xref chain at all can be found (e.g. corrupt input). Verified against the existing fixtures: `unsigned` → 1, `signed` → 2, `signedThenIncrementallyModified` → 3 (unchanged from T03, now derived structurally instead of by marker count).
  - PDFBox never writes a linearized PDF (confirmed: `save`/`saveIncremental` only ever produce classic sequential or incremental layouts), so the linearized case is proven with a hand-built byte layout in `RevisionCounterTest` (two `xref`/`trailer` sections linked by `/Prev`, the first preceded by a minimal `/Linearized` dictionary) rather than a real fixture — documented as a limitation in the class Javadoc.
- **Raw `/Rotate` validity**: `PdfBoxDocumentReader` now distinguishes "the raw value truncated to `int` for reporting" from "is this raw value actually trustworthy", since truncation alone can hide an invalid value (e.g. `COSFloat 90.5` truncates to `90`, which looks like a valid multiple of 90). Only a `COSInteger`, or a `COSFloat` with no fractional part, is valid; anything else (non-integral float, non-numeric, or a name/string) is flagged invalid regardless of what its truncated int happens to be.
- **`PageInfo`**: `rotationValid` is now an explicit record component (previously derived purely from `rawRotation % 90`), supplied by the reader; the compact constructor enforces consistency: `rotationValid=true` requires `rawRotation` to be a multiple of 90 and `rotation` to equal its normalized value; `rotationValid=false` requires `rotation == DEG_0` (the documented fallback). Existing 6-arg call sites updated to the new 7-arg shape (mechanical).
- **Missing header**: `DocumentStructure.headerVersion` is now nullable (matching the existing `catalogVersion` convention) instead of a `@NonNull` field the reader threw `InvalidPdfException` for; `parseHeaderVersion` returns `null` when no `%PDF-x.y` match is found in the first 1024 bytes instead of throwing, since PDFBox itself can still load such a file (confirmed empirically: PDFBox logs `"Error: Header doesn't contain versioninfo"` and proceeds, defaulting the version from the catalog).

### T04 — BcSignatureVerifier

- **`infrastructure/bouncycastle/`** (new package; PDFBox used only for signature-dictionary access, BC for CMS — no PDFBox/BC type leaves the adapter):
  - **`BcSignatureVerifier`**: implements `SignatureVerifier`. Iterates `PDDocument#getSignatureFields()` (skipping unsigned fields) so each report carries its field name; evaluates each signature independently and defensively (`catch (IOException | RuntimeException)` around the whole per-signature evaluation) so one hostile/malformed signature can never abort the analysis of the others — only a whole-document parse failure (`Loader.loadPDF` itself throwing) raises `InvalidPdfException`. Uses a private `BouncyCastleProvider` instance passed to each builder rather than registering it globally.
  - **`SignatureByteRange`**: validates `/ByteRange` beyond what `ByteRangeCoverage` itself enforces — checks that the gap between the two signed ranges is delimited by `<`/`>` and its length matches the `/Contents` hex string exactly (`2 + 2*contents.length`), by inspecting the raw file bytes at the gap boundaries. Any structural violation (including one `ByteRangeCoverage` itself rejects, e.g. a negative or overflowing length) surfaces as `IllegalArgumentException`, mapped by the caller to `INVALID_SIGNATURE`.
  - **`CmsSignatureVerification`**: promotes the spike's proven approach (`ASN1InputStream.readObject()` → `ContentInfo` → `CMSSignedData(CMSProcessableByteArray, ContentInfo)`, tolerating PDFBox's zero-padded `/Contents`) rather than reimplementing it. `SignerInformation#verify(...)` checks both the signed `messageDigest` attribute against the actual digest of the ByteRange-covered bytes (tamper detection) and the signature itself. Orders the certificate chain signer-first by walking issuer/subject DNs until a self-signed (root) certificate is reached or no further issuer is found in the CMS; leftover certificates are appended rather than dropped.
  - **`X509CertificateInfoMapper`**: maps the extracted `java.security.cert.X509Certificate`s to the domain's library-free `CertificateInfo`, including OCSP/CRL URLs read from the Authority Information Access / CRL Distribution Points extensions (`cert.getExtensionValue(oid)` → unwrap the outer `OCTET STRING` → parse the inner DER with the matching BC ASN.1 type). A malformed extension does not fail the certificate; it simply yields no URLs for it.
  - **Subfilters**: `adbe.pkcs7.detached` and `ETSI.CAdES.detached` are verified; `adbe.pkcs7.sha1`, `adbe.x509.rsa_sha1`, `ETSI.RFC3161` (a document timestamp signature — T05) and anything unrecognized are reported `UNSUPPORTED` without attempting CMS parsing.
  - **Multi-signature semantics**: each signature's `IntegrityStatus` is `INTACT` when its `ByteRangeCoverage` reaches the actual end of the file, `MODIFIED_AFTER_SIGNING` otherwise (a later incremental update — including a second signature — was appended after it). For a doubly-signed document this means the first signature is `MODIFIED_AFTER_SIGNING` and the last is `INTACT`, which is documented as expected PDF behavior rather than a defect, both in `BcSignatureVerifier`'s Javadoc and the README.
  - **Domain addition**: `ByteRangeCoverage.unknown(fileLength)` — a placeholder (`[0,0,0,0]` over the real file length) used only when the raw `/ByteRange` is too broken to report meaningfully, satisfying the record's own invariants (matches the existing `NOT_CHECKED`/`absent()` placeholder convention already used elsewhere in the domain).

### T04b — Verifier robustness

- **`SignatureByteRange`** (`infrastructure/bouncycastle/`): the gap-length check previously compared the `/ByteRange` gap against `2 + 2*signature.getContents(pdf).length` — but `getContents(pdf)` itself computes its byte extent purely from `/ByteRange`'s own numbers (confirmed by disassembling PDFBox 3.0.8's `PDSignature` bytecode with `javap -c`: `byteRange[0]+byteRange[1]+1` to `byteRange[2]-1`), so the check was comparing the gap against a length derived from that same gap — a tautology that can never fail. Fixed to use `signature.getContents()` (no-arg), which PDFBox resolves independently by walking its own parsed object structure (xref → dictionary → `/Contents` `COSString`), never touching the `/ByteRange` array. The `<`/`>` boundary-byte checks (using the raw file bytes, which is a legitimate structural check) are unchanged.
  - Test: new `SignatureByteRangeTest` (package-private class tested directly, in the same package). Constructing a real PDFBox-loaded PDF where `/ByteRange` and `/Contents` disagree turned out to be impractical — in a real, honestly-parsed file the two always agree (both ultimately read the same physical bytes), which is exactly why the old check could never fail either. Instead the test hand-builds a minimal `byte[]` and a bare `PDSignature` (`setByteRange`/`setContents` called directly, no file parsing involved), giving full control over both values independently.
- **`RevisionCounter`** (`infrastructure/pdfbox/`): previously, each hop of the backward `/Prev` walk rescanned from its own offset to the end of the file for the `stream`/`startxref`/`/Prev` keywords — `O(hops × file size)`. Replaced with a single forward scan per keyword collecting all its occurrences once (`MarkerPositions.scan`, `O(n)`), and each hop now does a binary search over those sorted positions (`O(log n)`) instead of rescanning — total `O(n log n)`. The already-visited-offsets guard (unchanged) still bounds a cyclic `/Prev` chain; an out-of-range `startxref` still falls back to the `%%EOF`-marker heuristic exactly as before (verified this was already correctly handled, just needed a test).
  - Re-verified the linearized-layout hand-built test already matched the real linearized shape (`/Linearized` dict + first-page xref near the start + main xref at the end linked by `/Prev`) from T03b — no change needed there, just confirmed.
  - Tests: cyclic `/Prev` (two sections referencing each other; the visited-offsets guard stops the walk at 2, not an infinite loop), out-of-range `startxref` (falls back to `%%EOF` count, never throws), and a ~4.7 MB synthetic file with 2000 chained revisions counted in well under 3 s (proving `O(n log n)`, not quadratic).
- **`BcSignatureVerifier`**: two independent gaps fixed.
  1. Only `evaluateUnsafe` (the CMS/`ByteRange` step) was guarded against `RuntimeException`; reading the field itself (`PDSignatureField#getSignature()`/`#getFullyQualifiedName()`) happened *before* that guard, in the `verify(byte[])` loop directly. A hostile field throwing there would have escaped the whole method. Restructured into a new package-private `evaluateField(byte[], PDSignatureField)` (visibility relaxed from private to package-private specifically so it can be unit-tested directly with a Mockito-mocked `PDSignatureField`) that wraps the *entire* per-field read+evaluation in one guard.
  2. A CMS that verified successfully but whose certificate chain contained one certificate that failed to re-encode to DER (`X509CertificateInfoMapper.toDomain`, `CertificateEncodingException`) previously let that exception propagate up through `evaluateUnsafe`'s own try/catch, which reported `INVALID_SIGNATURE` — even though the signature itself was valid. Added `X509CertificateInfoMapper.toDomainResilient(List<X509Certificate>)`, mapping what it can and counting failures instead of aborting; `BcSignatureVerifier` now reports the real `IntegrityStatus`, the (possibly partial) chain, and a new `SignatureReport.anomaly` note when any certificate could not be mapped.
  - Domain addition: `SignatureReport` gained `anomaly` (nullable `String`, `anomalyOptional()`), following the same nullable-with-`Optional`-accessor convention already used for `claimedSigningTime`.
  - Test: `aSignatureFieldThatThrowsWhileBeingReadIsReportedInvalidNotAnException` (Mockito-mocked `PDSignatureField#getSignature()` throwing `IllegalStateException`, calling `evaluateField` directly) and `anUnsignedFieldReportsNothing`. The certificate-mapping-resilience path itself is implemented and code-reviewed but not separately fixture-tested at the `BcSignatureVerifier` level: producing a real signed PDF whose embedded, CMS-verified certificate cannot be DER-re-encoded is not practically constructible (a `JcaX509CertificateConverter`-produced certificate always re-encodes successfully); the resilient-mapping mechanism itself is exercised implicitly by every existing chain-extraction test continuing to pass unchanged.

### T05 — RFC 3161 signature timestamps

- **`SignatureTimestampVerifier`** (new, `infrastructure/bouncycastle/`): extracts the unsigned CMS attribute `id-aa-signatureTimeStampToken` (`PKCSObjectIdentifiers.id_aa_signatureTimeStampToken`) from a `SignerInformation`, parses it as a Bouncy Castle `org.bouncycastle.tsp.TimeStampToken`, and verifies:
  1. **Message imprint**: recomputes the digest of `signerInformation.getSignature()` (the raw signature value bytes, not the document content) using the token's own declared imprint algorithm (`TimeStampTokenInfo#getMessageImprintAlgOID()`, via `JcaDigestCalculatorProviderBuilder`), and compares it to `getMessageImprintDigest()`.
  2. **TSA signature**: finds the TSA certificate embedded in the token (matched via `TimeStampToken#getSID()` against the token's own certificate store) and calls `TimeStampToken#validate(...)` (built with `JcaSimpleSignerInfoVerifierBuilder`); notes (without failing) when the TSA certificate is missing the `id-kp-timeStamping` extended key usage.
  - Never throws: no unsigned attribute or no attribute value → `TimestampInfo.absent()`; anything else going wrong (malformed ASN.1, `TSPException`, an unsupported/malformed imprint algorithm, a missing/malformed TSA certificate) is caught and reported as a present-but-invalid `TimestampInfo` with a diagnostic `note`, never propagated.
  - Wired into `CmsSignatureVerification.Result` (gained a `timestamp` field, computed unconditionally alongside the certificate chain) so `BcSignatureVerifier` never has to see Bouncy Castle's ASN.1/CMS/TSP types directly — it only ever sees the domain `TimestampInfo`.
- **Domain**: `TimestampInfo` extended (kept the existing `absent()`/`isPresent()` shape) with `signatureValid` (boolean), `tsaCertificate` (nullable `CertificateInfo`, `tsaCertificateOptional()`) and `note` (nullable `String`, `noteOptional()`); compact constructor keeps the one null-check that matters (`tsaName` non-null; callers pass `""` for "unknown/absent" rather than `null`, matching the existing `subFilter` convention in `BcSignatureVerifier`). `genTime` documented as the TSA's independently-verifiable claim vs. `SignatureReport.claimedSigningTime` (`/M`/`signingTime`), which stays purely self-declared.
- **Document timestamps** (`/Type /DocTimeStamp`, `ETSI.RFC3161` subfilter): **decision — kept `UNSUPPORTED`, not implemented**. Verifying a document timestamp is not a variation of the existing signature path: its CMS content is a bare `TSTInfo` (no signed document digest attribute, no signer certificate chain in the CAdES sense — the "chain" would be the TSA's own), so it needs its own report shape and its own CMS-parsing branch (parse as `TimeStampToken` directly, verify the imprint over the `/ByteRange`-covered bytes instead of over a signature value). Given the scope already covered (signature timestamps, the actually-required RFC 3161 capability per the TFM plan) and the time budget, this was judged not "straightforward" per the task's own instruction, and is deliberately deferred rather than silently skipped. The existing `aDocumentTimestampSubFilterIsReportedAsUnsupportedForNow` test is unchanged and still documents this.
