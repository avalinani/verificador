# Feature: pdf-validator

## Objective
Stateless web service (TFM) that audits a PDF in one pass: signature integrity (PAdES/CMS), post-signature modifications, RFC 3161 timestamps, X.509 chain trust, optional OCSP/CRL revocation, PDF/A-1b conformance, page properties.

### T03b — Reader robustness

- **Revision counting** (`infrastructure/pdfbox/RevisionCounter`, new class): walks the xref/trailer chain backwards from the last `startxref`, following each section's `/Prev` link (bounded to stop at the next `stream`/`startxref` keyword so an unrelated `/Prev`-looking byte sequence elsewhere in the file cannot be picked up), counting one hop per xref section. Detects a linearized layout by searching for a `/Linearized` marker in the first 2048 bytes and, when present, does not count the hint-section xref as a separate revision. Falls back to the previous `%%EOF`-marker heuristic only if no xref chain at all can be found (e.g. corrupt input). Verified against the existing fixtures: `unsigned` → 1, `signed` → 2, `signedThenIncrementallyModified` → 3 (unchanged from T03, now derived structurally instead of by marker count).
  - PDFBox never writes a linearized PDF (confirmed: `save`/`saveIncremental` only ever produce classic sequential or incremental layouts), so the linearized case is proven with a hand-built byte layout in `RevisionCounterTest` (two `xref`/`trailer` sections linked by `/Prev`, the first preceded by a minimal `/Linearized` dictionary) rather than a real fixture — documented as a limitation in the class Javadoc.
- **Raw `/Rotate` validity**: `PdfBoxDocumentReader` now distinguishes "the raw value truncated to `int` for reporting" from "is this raw value actually trustworthy", since truncation alone can hide an invalid value (e.g. `COSFloat 90.5` truncates to `90`, which looks like a valid multiple of 90). Only a `COSInteger`, or a `COSFloat` with no fractional part, is valid; anything else (non-integral float, non-numeric, or a name/string) is flagged invalid regardless of what its truncated int happens to be.
- **`PageInfo`**: `rotationValid` is now an explicit record component (previously derived purely from `rawRotation % 90`), supplied by the reader; the compact constructor enforces consistency: `rotationValid=true` requires `rawRotation` to be a multiple of 90 and `rotation` to equal its normalized value; `rotationValid=false` requires `rotation == DEG_0` (the documented fallback). Existing 6-arg call sites updated to the new 7-arg shape (mechanical).
- **Missing header**: `DocumentStructure.headerVersion` is now nullable (matching the existing `catalogVersion` convention) instead of a `@NonNull` field the reader threw `InvalidPdfException` for; `parseHeaderVersion` returns `null` when no `%PDF-x.y` match is found in the first 1024 bytes instead of throwing, since PDFBox itself can still load such a file (confirmed empirically: PDFBox logs `"Error: Header doesn't contain versioninfo"` and proceeds, defaulting the version from the catalog).
- **Malformed XMP test**: added (`TestPdfFactory.malformedXmpMetadata()` + `PdfBoxDocumentReaderTest`); the existing `catch (IOException | XmpParsingException)` → `PdfaDeclaration.NONE` path needed no production change, only a test proving it.

Iterates `PDDocument#getSignatureFields()` (skipping unsigned fields) so each report carries its field name; evaluates each signature independently and defensively (`catch (IOException | RuntimeException)` around the whole per-signature evaluation) so one hostile/malformed signature can never abort the analysis of the others — only a whole-document parse failure (`Loader.loadPDF` itself throwing) raises `InvalidPdfException`. Uses a private `BouncyCastleProvider` instance passed to each builder rather than registering it globally.
  - **`SignatureByteRange`**: validates `/ByteRange` beyond what `ByteRangeCoverage` itself enforces — checks that the gap between the two signed ranges is delimited by `<`/`>` and its length matches the `/Contents` hex string exactly (`2 + 2*contents.length`), by inspecting the raw file bytes at the gap boundaries. Any structural violation (including one `ByteRangeCoverage` itself rejects, e.g. a negative or overflowing length) surfaces as `IllegalArgumentException`, mapped by the caller to `INVALID_SIGNATURE`.
  - **`CmsSignatureVerification`**: promotes the spike's proven approach (`ASN1InputStream.readObject()` → `ContentInfo` → `CMSSignedData(CMSProcessableByteArray, ContentInfo)`, tolerating PDFBox's zero-padded `/Contents`) rather than reimplementing it. `SignerInformation#verify(...)` checks both the signed `messageDigest` attribute against the actual digest of the ByteRange-covered bytes (tamper detection) and the signature itself. ### T04b — Verifier robustness

- **`SignatureByteRange`** (`infrastructure/bouncycastle/`): the gap-length check previously compared the `/ByteRange` gap against `2 + 2*signature.getContents(pdf).length` — but `getContents(pdf)` itself computes its byte extent purely from `/ByteRange`'s own numbers (confirmed by disassembling PDFBox 3.0.8's `PDSignature` bytecode with `javap -c`: `byteRange[0]+byteRange[1]+1` to `byteRange[2]-1`), so the check was comparing the gap against a length derived from that same gap — a tautology that can never fail. ### T05 — RFC 3161 signature timestamps

- **`SignatureTimestampVerifier`** (new, `infrastructure/bouncycastle/`): extracts the unsigned CMS attribute `id-aa-signatureTimeStampToken` (`PKCSObjectIdentifiers.id_aa_signatureTimeStampToken`) from a `SignerInformation`, parses it as a Bouncy Castle `org.bouncycastle.tsp.TimeStampToken`, and verifies:

- **`infrastructure/pki/PkixCertificateChainValidator`** implements `CertificateChainValidator` with the JDK's own `java.security.cert.CertPathBuilder` + `PKIXBuilderParameters` (not Bouncy Castle — no library dependency needed for plain PKIX path building, keeping this adapter JDK-only). `setRevocationEnabled(false)` (T10's job); `setDate(Date.from(validationTime))` where `validationTime` is supplied by the caller (the use case, in T08, per the port's existing Javadoc convention).
  - **Status mapping design choice**: a successful `build()` → `TRUSTED`. On failure, the JDK's PKIX exceptions don't reliably distinguish "untrusted root" from "missing issuer" across JDK versions/providers, so an independent, simpler check classifies it: `isStructurallyComplete` walks the presented chain verifying each certificate's signature against the next one's public key (`X509Certificate#verify`) up to a self-signed certificate. If the chain reaches a self-signed cert, the root itself just isn't a configured trust anchor → `UNTRUSTED_ROOT`; if it never does (a `verify` fails partway, or the list runs out first), an issuer is missing → `INCOMPLETE_CHAIN`. `EXPIRED` is checked first and independently of PKIX (`CertificateInfo#isValidAt(validationTime)` on every certificate in the presented chain), so an expired certificate is reported as `EXPIRED` even if it would otherwise resolve to a trusted path. Empty input → `NOT_CHECKED`.
  - **Real bug found and fixed during TDD**: the first implementation only added the chain's non-target certificates (`subList(1, size)`) to the `CertStore`, on the assumption the target selector alone was enough — but `CertPathBuilder` needs the target/leaf certificate itself available in a `CertStore` too (the selector is only a matching *criterion*, not a certificate the builder already holds), so path building always failed with `SunCertPathBuilderException: unable to find valid certification path to requested target`. Fixed by adding the *entire* certificate list to one `CertStore`. Diagnosed with `-Djava.security.debug=certpath`.
  - **Second real bug found and fixed**: after the first fix, the "trusted root" test still failed the same way. Diagnostic printing (`X509CertSelector.match: subject DNs don't match`) traced it to `TestPki`: certificates whose issuer field was built via `new X500Name(otherCert.getSubjectX500Principal().getName())` (re-parsing the JDK's RFC 2253 string form) end up with their issuer's RDN sequence DER-encoded in the *reverse* order relative to that other certificate's own subject field — a BC `X500Name(String)` literal encodes RDNs in the string's own left-to-right order, while JDK's RFC 2253 rendering always reverses whatever DER order it finds, so round-tripping through the string reverses it again relative to a directly-authored literal. BC's own DN comparisons (used elsewhere for CMS/CAdES chain matching) tolerate this; JDK's exact `X500Principal.equals()` (used by PKIX) does not. Fixed in `TestPki` with a `subjectName`/`issuerName` helper pair that rebuilds the BC `X500Name` straight from the principal's own DER bytes (`X500Name.getInstance(ASN1Sequence.getInstance(principal.getEncoded()))`), never through its string form; applied at all issuer-construction call sites (`buildTsaCertificate`, `buildEndEntityCertificate`, the new `buildIntermediateCertificate`/`buildEndEntityCertificateIssuedBy`, and `reissueWithoutTimestampingEku`). Full suite re-verified green after the fix (no regression in the other 128 pre-existing tests, which never happened to exercise exact JDK DN equality).

### T09c — Real-world signature false negatives

**Diagnosis, verified against two real user PDFs** (never copied into the repo, not even derived bytes — read transiently only via a scratch classpath outside the repo, `$TEMP/pdfval-debug`, deleted after use):

1. **Real PDF A** (Camerfirma, AES-256 encrypted, `adbe.pkcs7.detached`): `SignerInformation.verify(...)` built from an `X509CertificateHolder` (not a bare `PublicKey`) additionally checks the certificate's own validity at the CMS `signingTime` attribute and threw `CMSVerifierCertificateNotValidException` because the signer certificate's `notAfter` (2026-05-08) was before the declared signing time (2026-09-24) — a real signature made months after its own certificate expired. The report showed `INVALID_SIGNATURE`, empty chain, `anomaly: null`.
2. **Real PDF B** (FNMT, not encrypted, `adbe.pkcs7.detached`, **no signed attributes at all** — a legacy-style CMS): `SignerInfo.digestAlgorithm` = `1.2.840.113549.1.1.11` (`sha256WithRSAEncryption`, a SIGNATURE algorithm OID) instead of `2.16.840.1.101.3.4.2.1` (`sha256`), and `digestEncryptionAlgorithm` = bare `rsaEncryption` (`1.2.840.113549.1.1.1`, no digest implied). Two chained bugs, the second found only by testing against the real file (a first synthetic reproduction *with* signed attributes passed even before any fix, proving nothing): (a) Bouncy Castle's digest-calculator lookup fails with `NoSuchAlgorithmException` for the mislabeled OID; (b) even after fixing that, `SignerInformation#verify(...)` still returned `false` — diagnosed by disassembling `SignerInformation.class` from `bcpkix-jdk18on` 1.86 (`javap -c`): for a CMS with no signed attributes and an RSA signature, it reconstructs the expected PKCS#1 `DigestInfo` directly from the (mislabeled) `digestAlgorithm` field; its own `translateBrokenRSAPkcs7` helper only corrects the historical SHA-1 variant of this exact bug, never SHA-224/256/384/512 — so the reconstructed `DigestInfo` embeds the wrong OID and can never match the real signature.

**Fixes** (`infrastructure/bouncycastle/CmsSignatureVerification.java`, `BcSignatureVerifier.java`, new `DigestAlgorithmOidNormalizer.java`/`NormalizingDigestCalculatorProvider.java`):
- Crypto verification now always builds the `SignerInformationVerifier`'s content-verifier provider from the signer's bare public key (never the certificate holder), so Bouncy Castle never performs its own certificate-validity-at-signingTime check; certificate validity at the declared signing time is checked independently and surfaced as an `anomaly` note (never fails integrity). Chain trust/expiry (`chainStatus`) was already computed correctly by `PkixCertificateChainValidator` at the claimed signing time — it just never ran, because the signature was rejected first.
- `digestAlgorithm` OIDs that are themselves unambiguous signature-algorithm OIDs (RSA PKCS#1 v1.5, ECDSA, classic DSA — see `DigestAlgorithmOidNormalizer`'s table) are normalized for digest computation, **and** verified through a dedicated bypass (`verifyWithMislabeledDigestAlgorithm`) that never calls `SignerInformation#verify(...)`: it builds a `ContentVerifier` directly from the mislabeled-but-complete OID, checking the `messageDigest` attribute first when signed attributes are present, or verifying directly over the signed bytes when they are not — sidestepping Bouncy Castle's internal (buggy, for this case) `DigestInfo` reconstruction entirely.
