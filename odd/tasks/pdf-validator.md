# Feature: pdf-validator

## Objective
Stateless web service (TFM) that audits a PDF in one pass: signature integrity (PAdES/CMS), post-signature modifications, RFC 3161 timestamps, X.509 chain trust, optional OCSP/CRL revocation, PDF/A-1b conformance, page properties.

### T03b — Reader robustness

- **Revision counting** (`infrastructure/pdfbox/RevisionCounter`, new class): walks the xref/trailer chain backwards from the last `startxref`, following each section's `/Prev` link (bounded to stop at the next `stream`/`startxref` keyword so an unrelated `/Prev`-looking byte sequence elsewhere in the file cannot be picked up), counting one hop per xref section. Detects a linearized layout by searching for a `/Linearized` marker in the first 2048 bytes and, when present, does not count the hint-section xref as a separate revision. Falls back to the previous `%%EOF`-marker heuristic only if no xref chain at all can be found (e.g. corrupt input). Verified against the existing fixtures: `unsigned` → 1, `signed` → 2, `signedThenIncrementallyModified` → 3 (unchanged from T03, now derived structurally instead of by marker count).
  - PDFBox never writes a linearized PDF (confirmed: `save`/`saveIncremental` only ever produce classic sequential or incremental layouts), so the linearized case is proven with a hand-built byte layout in `RevisionCounterTest` (two `xref`/`trailer` sections linked by `/Prev`, the first preceded by a minimal `/Linearized` dictionary) rather than a real fixture — documented as a limitation in the class Javadoc.
- **Raw `/Rotate` validity**: `PdfBoxDocumentReader` now distinguishes "the raw value truncated to `int` for reporting" from "is this raw value actually trustworthy", since truncation alone can hide an invalid value (e.g. `COSFloat 90.5` truncates to `90`, which looks like a valid multiple of 90). Only a `COSInteger`, or a `COSFloat` with no fractional part, is valid; anything else (non-integral float, non-numeric, or a name/string) is flagged invalid regardless of what its truncated int happens to be.
- **`PageInfo`**: `rotationValid` is now an explicit record component (previously derived purely from `rawRotation % 90`), supplied by the reader; the compact constructor enforces consistency: `rotationValid=true` requires `rawRotation` to be a multiple of 90 and `rotation` to equal its normalized value; `rotationValid=false` requires `rotation == DEG_0` (the documented fallback). ### T04 — BcSignatureVerifier

- **`infrastructure/bouncycastle/`** (new package; PDFBox used only for signature-dictionary access, BC for CMS — no PDFBox/BC type leaves the adapter):
  - **`BcSignatureVerifier`**: implements `SignatureVerifier`. Iterates `PDDocument#getSignatureFields()` (skipping unsigned fields) so each report carries its field name; evaluates each signature independently and defensively (`catch (IOException | RuntimeException)` around the whole per-signature evaluation) so one hostile/malformed signature can never abort the analysis of the others — only a whole-document parse failure (`Loader.loadPDF` itself throwing) raises `InvalidPdfException`.   - **`SignatureByteRange`**: validates `/ByteRange` beyond what `ByteRangeCoverage` itself enforces — checks that the gap between the two signed ranges is delimited by `<`/`>` and its length matches the `/Contents` hex string exactly (`2 + 2*contents.length`), by inspecting the raw file bytes at the gap boundaries. ### T06 — PKIX certificate chain validator + trust store

- **`infrastructure/pki/PkixCertificateChainValidator`** implements `CertificateChainValidator` with the JDK's own `java.security.cert.CertPathBuilder` + `PKIXBuilderParameters` (not Bouncy Castle — no library dependency needed for plain PKIX path building, keeping this adapter JDK-only). `setRevocationEnabled(false)` (T10's job); `setDate(Date.from(validationTime))` where `validationTime` is supplied by the caller (the use case, in T08, per the port's existing Javadoc convention).
  - **Status mapping design choice**: a successful `build()` → `TRUSTED`. On failure, the JDK's PKIX exceptions don't reliably distinguish "untrusted root" from "missing issuer" across JDK versions/providers, so an independent, simpler check classifies it: `isStructurallyComplete` walks the presented chain verifying each certificate's signature against the next one's public key (`X509Certificate#verify`) up to a self-signed certificate. If the chain reaches a self-signed cert, the root itself just isn't a configured trust anchor → `UNTRUSTED_ROOT`; if it never does (a `verify` fails partway, or the list runs out first), an issuer is missing → `INCOMPLETE_CHAIN`. `EXPIRED` is checked first and independently of PKIX (`CertificateInfo#isValidAt(validationTime)` on every certificate in the presented chain), so an expired certificate is reported as `EXPIRED` even if it would otherwise resolve to a trusted path. Empty input → `NOT_CHECKED`.
  - **Real bug found and fixed during TDD**: the first implementation only added the chain's non-target certificates (`subList(1, size)`) to the `CertStore`, on the assumption the target selector alone was enough — but `CertPathBuilder` needs the target/leaf certificate itself available in a `CertStore` too (the selector is only a matching *criterion*, not a certificate the builder already holds), so path building always failed with `SunCertPathBuilderException: unable to find valid certification path to requested target`. Fixed by adding the *entire* certificate list to one `CertStore`. Diagnosed with `-Djava.security.debug=certpath`.
  - **Second real bug found and fixed**: after the first fix, the "trusted root" test still failed the same way. Diagnostic printing (`X509CertSelector.match: subject DNs don't match`) traced it to `TestPki`: certificates whose issuer field was built via `new X500Name(otherCert.getSubjectX500Principal().getName())` (re-parsing the JDK's RFC 2253 string form) end up with their issuer's RDN sequence DER-encoded in the *reverse* order relative to that other certificate's own subject field — a BC `X500Name(String)` literal encodes RDNs in the string's own left-to-right order, while JDK's RFC 2253 rendering always reverses whatever DER order it finds, so round-tripping through the string reverses it again relative to a directly-authored literal. BC's own DN comparisons (used elsewhere for CMS/CAdES chain matching) tolerate this; JDK's exact `X500Principal.equals()` (used by PKIX) does not. Fixed in `TestPki` with a `subjectName`/`issuerName` helper pair that rebuilds the BC `X500Name` straight from the principal's own DER bytes (`X500Name.getInstance(ASN1Sequence.getInstance(principal.getEncoded()))`), never through its string form; applied at all issuer-construction call sites (`buildTsaCertificate`, `buildEndEntityCertificate`, the new `buildIntermediateCertificate`/`buildEndEntityCertificateIssuedBy`, and `reissueWithoutTimestampingEku`). Full suite re-verified green after the fix (no regression in the other 128 pre-existing tests, which never happened to exercise exact JDK DN equality).
- **`infrastructure/pki/TrustAnchorProvider`**: loads trust anchors additively from (a) a fixed list of bundled classpath `truststore/*.pem` files (listed explicitly rather than scanned, since classpath directory listing differs between an exploded `target/classes` and a packaged jar), (b) an optional external directory (one certificate per file, PEM or DER), (c) an optional PKCS#12 keystore file — both (b)/(c) are plain constructor parameters for now, per the task's own note that Spring property wiring is T09's job. `TrustAnchorProvider.of(X509Certificate...)` is a test/DI convenience bypassing all I/O.

**Fixes** (`infrastructure/bouncycastle/CmsSignatureVerification.java`, `BcSignatureVerifier.java`, new `DigestAlgorithmOidNormalizer.java`/`NormalizingDigestCalculatorProvider.java`):

Chain trust/expiry (`chainStatus`) was already computed correctly by `PkixCertificateChainValidator` at the claimed signing time — it just never ran, because the signature was rejected first.

### T10 — OCSP/CRL revocation checking

- **`infrastructure/revocation/`** (new package): `OcspClient` (RFC 6960 — builds the request with BC `OCSPReqBuilder`/`JcaCertificateID` and a random 16-byte nonce, verifies responder identity — direct issuer or a delegated responder with `id-kp-OCSPSigning`, issued by the issuer —, response signature, `CertID` match, `thisUpdate`/`nextUpdate` freshness with a 5-minute clock-skew margin, and nonce echo when present), `CrlClient` (RFC 5280 — parses with plain JDK `CertificateFactory`/`X509CRL`, no BC needed for this part, verifies the CRL signature against the issuer's public key, freshness, looks up the serial number), `CompositeRevocationChecker implements RevocationChecker` (OCSP first, CRL fallback when OCSP is unavailable/inconclusive; every failure mode maps to `UNKNOWN` with a stable, non-sensitive reason, never throws).
- **Security review mid-task (two rounds, both addressed before any commit)**:
  1. **DNS-rebinding SSRF (critical)**: the first version resolved an AIA/CDP hostname with `RevocationUrlGuard` and then let `java.net.http.HttpClient` resolve the *same* hostname again at connect time — a hostile authoritative DNS server could answer those two lookups differently (public address for the check, private address for the real connection), defeating the guard. Fixed by resolving **exactly once**: `RevocationUrlGuard.resolve(url, allowPrivateAddresses, HostResolver)` returns a `ValidatedTarget(URI, InetAddress)`; `PinnedHttpClient` (new, a minimal HTTP/1.1 client built on a plain `Socket`, not `java.net.http.HttpClient`, which offers no public way to pin a resolved address in this JDK) connects directly to that one address. Only `http` is supported now — TLS SNI/hostname verification while pinning to an IP is possible (`SSLSocketFactory#createSocket(Socket,String,int,boolean)`) but was judged out of proportion for an optional, best-effort, already time-bounded feature; `https` AIA/CDP URLs are rejected with an explicit `UNKNOWN` reason instead. The SSRF denylist was also widened: IPv6 unique-local (`fc00::/7`, not covered by `Inet6Address#isSiteLocalAddress`), CGNAT (`100.64.0.0/10`), `0.0.0.0/8`, and IPv4-mapped IPv6 (normalized to its embedded IPv4 address before the IPv4 checks, so `::ffff:10.0.0.1` cannot slip past them).

See `AnalyzePdfUseCase#resolveRevocation`'s Javadoc and README §2.12/§10 for the full rationale.

## T19 Security hardening, block 2: trusted validation time
Objective: close the two audit findings on the instant the signer chain is validated at. CRITICAL: `SignatureTimestampVerifier` verified a timestamp only against the certificate carried by the token itself, and `AnalyzePdfUseCase.resolveValidationTime` used its `genTime`, so a holder of an expired-but-once-legitimate key could sign today, forge a timestamp with a self-made TSA and get `TRUSTED`/`VALID`. HIGH: without a timestamp the signer-declared date (`/M`, CMS `signingTime`) was used, with the same effect.
Branch `fix/trusted-validation-time` (from master cbbc5c0), not pushed. Route: delegated direct (single writer). TDD: strict, runner `./mvnw`.
User decision (binding, ETSI-style): the signer chain is validated at a timestamp `genTime` only when the timestamp is TRUSTED; otherwise at the current time (`Clock`). The declared signing time is informational only. UI text: "Sin sello de tiempo de confianza: se ha validado a fecha de hoy". Accepted consequence: no trusted timestamp + certificate expired since -> `NOT_ADMITTED` (`CHAIN_EXPIRED`).
- [x] T19a Domain + adapter: `TimestampInfo` gains `tsaChain` (TSA first, only issuer-linked certificates), `tsaTimeStampingEku`, `trusted` + `withTrust`; `SignatureTimestampVerifier` reports chain and EKU, never sets `trusted`. Commit be5ad96.
- [x] T19b Application: `assessTimestamp` (imprint + signature + EKU + `genTime` <= now + 5 min + TSA chain TRUSTED at `genTime` through the `CertificateChainValidator` port); `resolveValidationTime` = trusted `genTime` else `clock.instant()`; `SignatureReport.withTimestamp`; policy reason `VALIDATED_AT_CURRENT_TIME`. Commit 21d5526.
- [x] T19c Real-certificate integration tests + fixtures (`TestPki.issueExpiredSigner`, `issueTsaIdentityUnder`, `issueTsaIdentity(Duration)`, `TestPdfSigner.signWithTimestamp(..., genTime)`, `signClaimingTime`). Commit a122dbe.
- [x] T19d API: `timestamp.trusted` (additive). Commit 3e0839e.
- [x] T19e UI: reason text, "Sello de tiempo (TSA no de confianza)", "Fecha declarada (no verificada)", timestamp note in the technical details. Commit a2e2905.
- [x] T19f README (§2.2, 2.6, 2.7, 2.10, 2.11, 2.13, 2.14, 6, 7, 10, 11) and this file.
Decisions: trust is decided in the application layer through the existing port (no PKIX duplication, no Bouncy Castle in the domain). EKU: presence required; RFC 3161 "critical and only" not enforced (chain trust is the control; several real TSAs omit the critical bit). Skew: 5 minutes ahead of the injected clock. The TSA chain passed to the validator contains only issuer-linked certificates, because the validator checks the validity of every certificate it receives and an unrelated embedded one must not decide trust. TSA revocation is out of scope (documented limitation).
Route declaration: writer (single, delegated direct: 2+ non-trivial files across layers); triggers: writer + preparation.
